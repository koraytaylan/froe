# Releasing

Releases are cut from `develop` and driven entirely by pushing a tag.
[`.github/workflows/release.yml`](../.github/workflows/release.yml) is
authoritative for what happens next; this document covers the decisions and
the manual edits it cannot make for you.

Publishing to crates.io is the project's only irreversible step. A published
version can be yanked but never replaced or deleted, and the three crates
publish in dependency order, so a mistake found late still leaves earlier
crates permanently on the registry. Everything before the tag push is cheap
to redo.

## Before tagging

* The full CI matrix is green **on the exact commit you intend to tag**, not
  merely on an earlier commit in the branch. The matrix covers Linux and
  macOS at stable and the minimum supported Rust version; a host-only local
  gate cannot stand in for it, because platform-specific failures are
  invisible until the other runner executes them.
* Any high-risk change in the range has completed the review in
  [`high-risk-changes.md`](high-risk-changes.md), and its safety case records
  whether that review was performed by a person or by an automated
  adversarial pass. A feature whose interoperability gate is still open stays
  labelled beta, and the release notes say so; a closed gate needs no
  caveat.
* The release pipeline runs the Oak interoperability suite itself, against the
  digest-pinned Sling image, and the publishing job depends on it. That is
  deliberate: the release notes assert that maintenance is verified against a
  named Oak build, and a claim published from a run at some earlier commit is
  not evidence about the artifact being released. Expect the tag to take
  correspondingly longer.

## The version bump

The workspace version lives in one place, but the crates also pin each other
by version, and those pins are **not** derived from it. A bump therefore
touches five sites:

| Site | What changes |
| --- | --- |
| `Cargo.toml` | `[workspace.package] version` |
| `crates/froe-export/Cargo.toml` | the `froe` dependency's `version` |
| `crates/froe-cli/Cargo.toml` | the `froe` and `froe-export` dependencies' `version` |
| `Cargo.lock` | the three workspace entries, regenerated by any cargo command |

The pins matter because `cargo publish` strips `path` and keeps only the
version requirement. A pin left at the previous minor does not match the new
one — `^0.4.0` does not admit `0.5.0` — so the registry sees a crate that
requires its sibling's *old* release. Whether that fails loudly depends on
the crate: one that only uses API present in the old version publishes
successfully with a wrong requirement, while one that uses newly added API
fails its verification build. Because publishing runs `froe`, then
`froe-export`, then `froe-cli`, that failure arrives after the earlier crates
are already permanent. Grep the tree for the outgoing version before
committing; the only remaining matches should be in `Cargo.lock`.

The bump is its own `chore:` commit whose body records the semantic-versioning
rationale — what in the release is additive, and what, if anything, is
source-breaking for downstream code. Pre-`1.0` minors may carry breaking
changes, so state the reasoning rather than leaving it inferred.

## Tagging and pushing

Push the branch first, wait for its CI matrix, and only then push the tag.
Splitting the two is what makes a platform-specific failure stoppable: the
release workflow's own verification runs the same matrix, but a tag that has
already been pushed cannot be un-published if anything downstream of
verification succeeds.

Tags are annotated and named `vX.Y.Z`, with a message summarising the release
and repeating any beta caveat. The workflow refuses to proceed unless the tag
name matches the workspace version.

```console
$ git push origin develop
# wait for the branch matrix to pass
$ git tag -a v0.5.0 -F <message-file>
$ git push origin v0.5.0
```

## What the tag runs

Verification, then the changelog and release notes from the
conventional-commit history, then the release binaries for each shipped
target, then the GitHub release with checksums, and finally the crates.io
publish. Every step converges on re-runs — already-published versions are
skipped — so a release that fails partway is finished by pushing the same tag
again rather than by inventing a new version.

## Afterwards

The workflow fast-forwards `main` to the released commit once the crates are on
the registry, so `main` always names a version whose publish actually
succeeded. It refuses rather than merges if `main` has diverged, because a
branch advertised as the latest release is worse than a historical one when it
silently lags: it looks authoritative. If that job fails, reconcile `main`
deliberately instead of re-running it.

Confirm the outcome from outside the workflow that produced it:

* each crate's new version is in the sparse index cargo actually reads
  (`https://index.crates.io/fr/oe/<crate>`);
* the published inter-crate requirements name the new version, not the
  previous one;
* the GitHub release is not a draft and carries every platform archive plus
  its checksum file.

A release that needs correcting is superseded by a new patch version. Yanking
removes a version from dependency resolution for new consumers; it does not
remove the bytes, and it does not help anyone who already resolved it.
