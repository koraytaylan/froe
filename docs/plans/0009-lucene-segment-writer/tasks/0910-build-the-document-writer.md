# Build The Document Model And Bounded Inverted Indexer

The public writer: `Document` with `Field`s — name, `IndexOptions`, tokens (term bytes, position increment, start and end offsets) plus the token stream's end state (`final_position_increment`, `final_offset`, what Lucene reads from a token stream once its tokens are consumed), optional stored value, optional doc value, `omit_norms`, boost (a boost other than 1 on an `omit_norms` field and a first token with position increment 0 are typed refusals, the two documents Lucene's own inverter rejects) — and `LuceneIndexWriter::new(segment_directory, runs: RunLocation, budget: SortBudget)` (its spills go to the run location, never into the segment directory), which opens the stored-fields files on the first document (so `finish()` with no documents leaves no `_0` file) because they stream per document and takes the memory budget its spills respect (plan 0010 passes the reindex's sort budget), `add_document`, and `finish()`, which merges the runs, completes the segment in that directory and returns the file set it wrote (the two-file set of a zero-segment commit, the five-file set of a single compound segment) — plan 0010 hands it a directory inside the run's subdirectory and copies the files into `:data` afterwards. Several `Field`s of one name in one document compose as Lucene's own inverter composes them: after each value the end state's position increment and end offset are added, then the position-increment gap of 0 and the offset gap of 1 for analyzed fields, boosts multiply into one norm, and the norm's token and overlap counts sum over the values; Oak relies on this for every multi-valued property. Inversion accumulates postings per field in bounded memory: `(field, term, document, frequency, positions)` records are spilled as sorted runs through `SortedRuns` (plan 0007's generic external sort, crate-internal and instantiated here with a postings record type; only its `RunLocation`, `SortBudget`, `SortedPasses`, `SortedPass` and the `SpillRecord` bound are public) and merged into the postings and terms writers field by field; stored fields stream out as documents arrive; doc values are gathered per field with the same spill discipline, but their spills are *re-readable*: the doc-values writer walks its input several times (a statistics pass, the missing bitset, then the write), so each doc-value and norms run is read through task 0702's `into_sorted_passes()`, whose `pass()` method rewinds it and which keeps its files until the `SortedPasses` is dropped, charged as one extra open file, and a `SORTED` or `SORTED_SET` field costs two `SortedRuns` instances — one keyed by `(value, document)` to build the dictionary and assign ordinals, one keyed by `(document, ordinal)` to emit `docToOrd` (and, for sorted sets, `docToOrdCount` and `ords`) in document order — both counted in the budget, the open-file bound and the merge-pass counter; norms need one byte per document per field with norms, computed from each document's token count less its overlapping tokens (position increment 0, which the default similarity's norm discounts) as it arrives and kept (or spilled) until the field is written, charged to the same budget; merges run one at a time, per format rather than per field — the whole postings merge drained first (writing `.doc`, `.pos`, `.pay` and then `.tim`/`.tip` field by field), then the doc-value merge, then the norms merge, as the architecture's assembly order has it and as the single-file-pair doc-value and norms consumers require — so the open-file bound is the external sort's fan-in plus one for the spill inputs plus a named constant for the segment's own outputs open at once (the stored-fields pair and the files of the format being written) — the spill half pinned by the accounting test, the segment half bounded by construction and asserted as such, since the five outputs are counted at the one place that opens them rather than observed; a merge-pass counter pins the cost statement; field infos accumulate across documents under the rule stated below. A term longer than Lucene's maximum term length of 32,766 bytes is skipped exactly as Lucene skips it — the inversion catches the over-long term, drops it, keeps the document and still counts the position in the field's norm length — because Oak feeds `propertyIndex` strings unguarded (only sorted doc values are truncated, by Oak's own truncation); the skip is reported in the writer's statistics, never refused. Field infos compose across documents as Lucene composes them: index options downgrade to the lesser, `omitNorms` is sticky once true, and a doc-values type change is refused as Lucene refuses it. The library's capability row lands here.

**Steps:**

1. `writer/mod.rs` (declared `pub mod writer;` in `lucene/mod.rs` and re-exported from `lib.rs`), a `WorkUnit::IndexDocuments` variant in `progress.rs` with its noun arms for plan 0010's `writing index segments` step, and `writer/inverted.rs`, which keeps one per-field document counter — incremented when a document contributes its first term to that field, exactly as Lucene's own inversion counts visited documents — and hands it to task 0905's `finish_field` as `FieldStatistics.document_count` beside the two running sums, a cost of one counter per field and nothing charged to the spill budget, since the merge stream keyed `(field, term, document)` cannot recover distinct documents per field without a structure proportional to the segment; and with one shared `SortBudget` covering postings, doc values, norms and the terms writer's pending blocks — every spilling structure charged against a single total, since the field set appears as documents arrive and no static split exists (the terms writer's pending list: a field's open prefixes, each carrying the compiled index of a sub-block already written, stay resident until the field finishes, roughly the field's term count divided by the minimum block size of 25), and the same limit tests the other bounded structures have.
2. Tests: the budget-limit, open-file-accounting and merge-pass assertions as in-crate `#[cfg(test)]` tests in `inverted.rs`, because the accounting task 0702 exposes is crate-internal and `lucene_writer_tests.rs` is a separate crate that cannot name `froe::external_sort` — the reason task 0704 places its merge regression in `property_collector.rs` rather than in its own integration file.
