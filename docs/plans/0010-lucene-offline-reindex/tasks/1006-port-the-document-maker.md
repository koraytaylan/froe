# Port Oak's Document Maker

Implement `DocumentMaker::make(node, path, rule) -> Option<Document>` producing plan 0009's document model: every branch of Oak's document maker — typed fields, `full:` analyzed fields with the analyzer's tokens, `:fulltext` node-scope values and the node name, `:path` stored, `:ancestors` tokens over the *parent* path and `:depth` over the node's own, `:nodeName` — added only when the rule indexes the node name (`indexNodeName` on the rule, or a property definition named `:nodeName`), with everything up to and including the first colon stripped (a `jcr:content` node yields the term `content` while the node name's `:fulltext` value keeps `jcr:content`) and the document forced dirty, so such a node yields a document even with no other indexable property — `:nullProps` and `:notNullProps`, ordered doc values with Oak's own truncation and its four guards (a multi-valued property yields no `:dv` field at all, warned and skipped; only the LONG, DATE, DOUBLE, BOOLEAN and STRING tags produce one; the value must pass the value-pattern gate, which is the definition's `ValuePattern`, a binary or a match-all pattern included outright and otherwise the value matched against the include prefixes, the exclude prefixes and the pattern; and a second field of the same `:dv` name is dropped rather than added; the truncation is the only length guard Oak applies, and an over-long `propertyIndex` term is passed on for plan 0009's writer to skip as Lucene does; that gate's property form stands in front of the typed fields' per-value loop while its bare value form stands inside the per-property pass's per-value analyzed, suggest, spellcheck and fulltext loop, so an excluded value contributes no field of any kind), facets through `facets.rs` (the `<property>_facet` field name, the U+001F path encoding, the two drill-down terms per value — the escaped full path and the bare dimension — and sorted-set doc values), suggest and spellcheck fields — the `:suggest` field taking the suggest helper's newline tokenizer when `suggestAnalyzed` is false and the definition analyzer, capped, when it is true (the flag read from the `suggestion` child with the definition-root fallback, task 1005), with a golden case for each, aggregates including relative-node fulltext fields with boosts, `useInExcerpt` stored values, the `maxFieldLength` cap, the document-time refusal for a DATE value that does not parse, naming the path, the property and the value — the one refusal this task raises rather than the definition load, because Oak's own path fails the commit there — and the `null` result for a node that produced nothing under a rule that does not index every node — where a binary property under an included type marks the document dirty unconditionally, the per-property pass's binary branch doing so whatever the extraction returned, so a node whose only indexable property is a binary without `jcr:mimeType`, or under the `skip` policy, still yields a document. `binaries.rs` defines the public `BinaryTextPolicy` — private fields, built through `BinaryTextPolicy::new(fallback)` and `with_pre_extracted_text_directory(PathBuf)` as `CompactionOptions` is built — beside `BinaryTextFallback::{Marker, Skip}` (both `pub`, reachable as `froe::index::lucene::documents::binaries` since task 1007 edits neither `lib.rs` nor `writer/mod.rs`), which `DocumentMaker::new` receives the way Oak's document maker receives its binary text extractor at construction, and supplies text for binary properties: nothing when the holding node has no `jcr:mimeType`, the gate Oak's own extraction applies first, whatever the policy; otherwise from the pre-extracted directory in the layout Oak's pre-extracted text store writes when the blob carries an external identity (with `stripLength`), and for the rest the `TextExtractionError` marker or nothing per the fallback; the text goes into the field Oak adds binary text to — `:fulltext` for the node and non-relative includes, `fullnode:<include path>` for a `relativeNode` include.

**Steps:**

1. The document maker adding fields in the order the specification states (positions, offsets and the stored-field sequence depend on it), the binary policy's text or marker written as a stored `:fulltext`/`fullnode:` value as Oak stores binary text, with norms decided per field kind (Lucene's own analyzed field, which Oak uses for `:fulltext`, the aggregates' `fullnode:<path>` fields and `:ancestors`, carries norms; Oak's own analyzed field, which it uses for `full:<name>` and `:spellcheck`, omits them) and the index options of Oak's two norm-omitting analyzed forms distinguished (`useInExcerpt`, hence stored, indexes with offsets — `DOCS_AND_FREQS_AND_POSITIONS_AND_OFFSETS`; the unstored form without them — so the fixture's default definition gives every `full:<name>` field offsets while `:fulltext`, `:spellcheck` and `:suggest` have none), boosts set on the field as Oak sets them and multiplied across same-named fields into one norm as plan 0009's writer composes them, a `BINARY` property reaching the typed fields yielding no field at all (the typed-field branch for binaries, OAK-12133, reached when a rule excludes `Binary` from `includePropertyTypes` while the definition is `propertyIndex`), the binary policy taken at construction so the maker is testable without the command, and the module doc of `binaries.rs` recording the departure from Oak's own binary-text extraction (no Tika) with its pointer into `docs/analysis/lucene-oak-documents.md`.
2. Tests: a golden set of nodes under the fixture's default definition and under synthetic definitions exercising every branch, each with the expected field list written by hand from the specification's worked examples, among them a definition carrying `valueIncludedPrefixes` and `valueExcludedPrefixes` over a two-value property whose excluded value contributes no typed, ordered, analyzed, suggest, spellcheck or fulltext field while its sibling contributes all of them, a node whose DATE property does not parse, asserting the refusal names the path, the property and the value, and a multi-valued ordered property contributing no `:dv` field at all while its typed and analyzed fields are unaffected — a content fact only this task's maker can observe, which is why task 1005's definition-side tests do not claim it.

- **Done when:** every golden field list matches, every unsupported feature is refused by name at definition load rather than at document time — the one document-time refusal being an unparseable DATE value, which Oak's own path also fails on — and the stable host gate passes; equality with Oak's own documents is task 1009's acceptance.
