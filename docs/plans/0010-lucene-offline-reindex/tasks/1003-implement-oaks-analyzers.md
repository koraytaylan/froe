# Implement Oak's Analyzers With Token-Level Conformance

Implement the chain as `Analyzer::tokens(field_name, text) -> TokenStreamResult { tokens: Vec<Token { term, position_increment, start_offset, end_offset, token_type }>, final_position_increment, final_offset }` — the end state being what Lucene reads from a token stream once its tokens are consumed, and what plan 0009's writer needs to compose several values of one field: the standard tokenizer over generated Unicode tables, the lower-case filter, the word delimiter filter with Oak's two flag sets, the shingle wrapper for `:spellcheck`, the path-hierarchy tokenizer for `:ancestors`, the newline-only suggest tokenizer for `:suggest`, and the token-count cap applied per field value to every field except `:spellcheck` and un-analyzed `:suggest`, whose per-field analyzers bypass it, not at all when `maxFieldLength` is negative, and with zero refused at definition load, as the specification states. No dependency and no new toolchain: the tables are generated by `crates/froe/examples/generate_unicode_tables.rs`, a Rust example the gate compiles with `--all-targets`, from the inputs task 1002 pins — the five Unicode Character Database files (`WordBreakProperty.txt`, `Scripts.txt`, `LineBreak.txt`, `Blocks.txt`, `UnicodeData.txt`), which the operator downloads with the command recorded in each table's header and passes to the example by path, the example verifying each against its pinned SHA-256 by running `sha256sum`, or `shasum -a 256` where coreutils is absent, through `std::process::Command` before reading it (the files are not committed; the tool requirement is recorded in each table's header), and the judge's enumeration of the image's own JVM case mapping (committed as `crates/froe/tests/fixtures/java-lower-case-table.tsv`) for the case map — and checked in as data under `analysis/unicode/`, one table per property with `#[rustfmt::skip]` packed rows so each stays under the thousand-line gate, each file's header recording the generating command, the input checksum and the generated table's own SHA-256; regenerated only deliberately.

**Steps:**

1. Judge class `judge/Analyze.java` with `analyze <mode> <corpus>` printing, for every line of a corpus, the token tuples and the end state — the end-state position increment and end offset — produced by the analyzer Oak builds for a synthetic Lucene definition: the default (capped at `maxFieldLength`), one with `indexOriginalTerm`, and one with `evaluatePathRestrictions` for the `:ancestors` chain, plus the per-field analyzers Oak's writer configuration installs for `:spellcheck` and `:suggest` (Oak's shared analyzer instance and a freshly constructed Oak analyzer are uncapped on their own; only the definition's own analyzer construction wraps them in the cap), and `lower-case-table` printing every code point the image's JVM lower-cases to something other than itself; commit it as `crates/froe/tests/fixtures/oak-analyzer-corpus.txt`, covering ASCII, case transitions, hyphens and underscores, apostrophes and possessives, digits inside words, CJK, Hangul, combining marks, emoji, astral characters, whitespace variants, newlines, repository paths, the 255-character token limit (for the suggest mode too, whose newline tokenizer splits a long line there — 255 UTF-16 code units checked after each code point, with an astral character at the boundary in the corpus), and a text above the 10,000-token cap (which the default and original-term modes cut and the spellcheck and suggest modes do not); the five modes are named `default`, `original-term`, `ancestors`, `spellcheck` and `suggest`, and the vector files carry those names; commit the judge's outputs as one vector file per mode and the lower-case table.
2. `analysis/mod.rs` registered as `pub mod analysis;` in `lucene/mod.rs`, with documented stubs for `analysis/numeric.rs` (task 1004 owns it) and `documents/mod.rs` (registered as `pub mod documents;`; task 1005 owns it), so 1004 and 1005 run in parallel without touching the Lucene module root; the tokenizers and filters; the generator example and the generated `unicode/` tables.
3. Tests replaying every vector for every mode, end state included, a test that the committed case table equals the generated one, a test hashing each generated Unicode table against the SHA-256 recorded in its own header (so a hand-edit is caught without the inputs), a structural invariant test per table (rows strictly ascending, non-overlapping, total over the code-point space with a declared default), and tests confirming the worked examples of `docs/analysis/lucene-oak-analysis.md` against the same vectors.

- **Done when:** every vector matches term, position increment, offsets, type and end state for all five modes, every worked example in the specification is confirmed by a vector, each generated table file is under a thousand lines, and the stable host gate passes.
