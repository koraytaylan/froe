# Specify Oak's Lucene Document Model

Write `docs/analysis/lucene-oak-documents.md`: from a node state to the exact set of Lucene fields, read at the pinned commit from Oak's own indexing sources — `oak-search/src/main/java/org/apache/jackrabbit/oak/plugins/index/search/**` for the definition model, the indexing rules, the property definitions, the aggregate rules, the fulltext editor and the shared document maker, and `oak-lucene/src/main/java/org/apache/jackrabbit/oak/plugins/index/lucene/**` for the Lucene definition, its own document maker, its field construction, its field naming and its writer configuration — together with the Lucene field and doc-value types `oak-lucene` vendors. Cite methods rather than whole files: the definition model alone runs past two thousand lines at the pinned commit. The facet field and the facet configuration are not vendored by Oak, so the document pins them as the Maven artifact `org.apache.lucene:lucene-facet:4.7.2:sources` by SHA-256 and records how it was obtained, exactly as task 1002 pins the analyzers. The task lands after 1002 because it owns the `docs/analysis/README.md` rows for both documents.

**Steps:**

1. Rules and the doc-value conversions. Record what an ordered `:dv<name>` field becomes: a numeric doc value, the double doc value that stores the raw bits of the double rather than the sortable-long encoding of the indexed double term, and the epoch-millisecond long a DATE is converted to. Record how a definition's rules are collected and how a rule is inherited — a rule marked `inherited` covers subtypes, and the applicable rule is resolved over the primary type before the mixins against the node-type hierarchy — what makes a rule index every node of a matching type, `includePropertyTypes`, `nodeTypeIndex`, the old-format detection that builds rules for a definition carrying no `indexRules` node and the refusal froe applies to it, and the codec selection: the `oak.lucene.compressing-codec` system property first, a consumer-JVM setting froe cannot observe and therefore a recorded departure, then an explicit `codec` resolved by registered name, then `oakCodec` when the definition is fulltext-enabled — a rule with node aggregates or a fulltext-enabled property definition — else `Lucene46`; froe refuses by name any definition whose verdict is not `oakCodec`. Record the definition-level `valueRegex`: which values the per-property pass skips under it, when the document maker still adds the node-name term, and how Oak's index writer drops a document left holding nothing but `:path` — refused by name by task 1005.
2. Property definitions: every field of a property definition — `index`, `propertyIndex`, `analyzed`, `nodeScopeIndex`, `ordered`, `useInExcerpt`, `useInSuggest`, `useInSpellcheck`, `facets`, `nullCheckEnabled`, `notNullCheckEnabled`, `boost`, `weight`, `type`, `isRegexp`, `name` including relative names and their `ancestors`, `valuePattern`, `excludeFromAggregation`, `sync`, `unique`, `function`, `dynamicBoost`, `useInSimilarity` — how a rule resolves a property name, the lookup being case-insensitive under Java's own case-insensitive string ordering, which the fixture's lower-cased names such as `sling:resourcetype` depend on, and how regular-expression definitions are matched: the pattern text is split at its last `/` into a parent path and a name expression, by the same parent-and-name split Oak applies to any path, so a leading `/` yields the parent `/`, which never equals a relative property path, while Oak's own catch-all name pattern is special-cased to an empty parent and the whole text; a match is then the property's parent path compared for equality followed by a whole-string regular-expression match of the name expression against the name. Quote the exact expression of that catch-all pattern. Precedence, stated once: rule order and property-definition order are the `:childOrder` of `indexRules` and `properties` as Oak yields child names, raw child order when that property is absent; rule resolution tries the primary type before the mixins and takes the first applicable rule; a name lookup takes an exact, case-insensitive hit before the name patterns, the first matching pattern wins, and the first of two case-insensitive duplicate property definitions is kept. The synthetic `:nodeName` goes through the same lookup as any property, and the name patterns are tried for hidden names too, which Oak keeps for bug compatibility, so under a definition whose pattern is `^[^\/]*$` — the fixture's default — the per-property pass adds a stored `full::nodeName` and a `:fulltext` value holding the node name before the document maker adds the node name to `:fulltext` again.
3. Fields: for every branch of the document maker record the field name, the Lucene field kind, index options, stored flag, norms, doc-value type, boost, and the value transformation. The branches are the per-property pass, the typed fields, the typed ordered fields, the null-check and not-null-check markers, the aggregate walk with its per-aggregated-node pass, the node-name field and the finalization. The ancestors branch is one of them: `:ancestors` is an analyzed field with norms over the node's *parent* path, while `:depth` is a numeric integer field over the depth of the node's own path. So is the consumer-registered field augmentation the maker calls: froe reproduces no consumer-registered field provider, an AEM safety invariant this document states. So is the doc-value type of `:dv<name>`, which follows each rule's own declared property type, so two rules typing one property differently produce one field name with two types and Oak drops the later documents, the writer refusing a doc-values type change and the fulltext editor catching that refusal per document. The value transformations: the value read converting to `STRINGS`, the epoch-millisecond conversion of a DATE, and Oak's own truncation of a sorted doc value at its maximum string length — a truncation for sorted doc values only, since a `propertyIndex` string becomes an unanalyzed term unguarded and Lucene's own inversion then skips a term above its maximum term length while keeping the document. Then the version-2 `full:` prefix, and the per-field analyzer each field is indexed with: Oak's analyzer, the `:ancestors` path-hierarchy chain, the `:suggest` tokenizer, the `:spellcheck` shingles, the token-count cap. Classify `:suggest` for norms and index options explicitly: no landed plan states them, and plan 0009's norms task enumerates the fields that carry norms and those that omit them without placing it. For a regular-expression definition Oak skips tokenization for a fixed set of names — `jcr:uuid` plus the user and group property names Oak's security module declares, transcribed here from `oak-security-spi` — which makes `full:<name>` an untokenized, unstored term field with `DOCS_ONLY`, even under `useInExcerpt`. Every value-bearing branch is gated by the property definition's value pattern — `valuePattern`, `valueIncludedPrefixes`, `valueExcludedPrefixes` — through one of the document maker's two inclusion tests: the property form, which includes a `BINARY` property and a match-all pattern outright and otherwise reads the value converting to `STRING` and matches it, and the bare value form, a plain pattern match. The property form stands in front of the `:dv` field and in front of the typed fields' per-value loop; the bare form stands inside the per-property pass's per-value analyzed, suggest, spellcheck and fulltext loop, which the definition-level `valueRegex` gates first — the two agree there, since a binary never reaches that loop and a match-all pattern implies a match — so a value the pattern excludes contributes no field of any kind, while the prefix forms of the pattern are the ones plan 0006 supports and this plan therefore reaches. Field addition order per name, which fixes positions, offsets and the stored-field sequence: the document opens with `:path`; the maker then walks the node's properties in the order the node state yields them, plus the synthetic `:nodeName`, adding per property the ordered doc values first — they precede the per-property pass, which is the only producer of typed fields on the paths this plan implements, the other being the function-restriction pass, which the `function` refusal excludes — then the typed fields, then, per value, `full:<name>`, `:suggest`, `:spellcheck` and `:fulltext`, then the facet field; then the aggregates, whose values arrive in the aggregated node's property order, the null, function and not-null markers, the dynamic boost and the consumer-registered field augmentation, the node-name field, the node name's `:fulltext` value, and the ancestors fields, with the facet configuration's build pass re-emitting the document — the facet-derived fields first, the rest in order — and the finalization re-adding the merged `:suggest` last, so a `:fulltext` field holds property values, then aggregate values, then the node name, and same-name fields are inverted in that order, each continuing from the previous field's end-state position and offset.
4. Aggregates: the include patterns — `path` as `/`-separated steps, each `*` or a literal child name, since no `**` step exists and an include element is compared literally, with `maxDepth` the number of steps and `primaryType` enforced on the last step only — then `primaryType`, `relativeNode`, `reaggregateLimit`, the matcher state machine, what a relative-node include changes in field names, and the aggregated-property rules.
5. Facets: the build pass over a sorted-set facet field — dimension and path joined with the U+001F unit separator, a U+001F or U+001E inside a component escaped with a U+001E prefix and an empty component refused, the `<property>_facet` index field name Oak sets on the field, the two drill-down term fields per facet value, which are the escaped full path and the bare dimension, both under `<property>_facet` and both unstored, beside the counting sorted-set doc value, and multi-valued dimensions — cited to the pinned `lucene-facet` sources. Oak's node-state-backed facet configuration persists into the *visible* definition: a `facets` child, `jcr:primaryType = nt:unstructured` when created, as soon as one facet property is indexed, whatever its arity, since the configuration is consulted for every facet property; with `facets/<each path element of the dimension>` carrying `jcr:primaryType = nt:unstructured`, a `NAME` set when absent, and `multivalued = true` for every multi-valued `STRINGS` dimension, written by the document maker at index time and read on the query side by nothing.
6. Binaries: Oak's own binary-text extraction — nothing without `jcr:mimeType` or for a type outside the Tika-supported set, the `TextExtractionError` marker only from the exception branches, an empty extraction stored as the empty string — then the pre-extracted text provider with the layout Oak's pre-extracted text store writes, its `stripLength` and `maxExtractLength`, the field the text is added to, which is `:fulltext` for the node and non-relative includes and `fullnode:<include path>` for a `relativeNode` include, and the fact that it is *stored*: binary text, and plan 0010's marker in its place, is a stored value of that field, unlike a `nodeScopeIndex` property value, which Oak's node-scope fulltext field leaves unstored; and why inline segment blobs cannot be pre-extracted.
7. Index-time bookkeeping Oak's fulltext editor performs around the writer: the definition it builds and the `refresh` flag that build consumes, the reindex mode it enters with the `:index-definition` clone and the `:version` property that go with it, what closing the writer writes — the `:status` node with its fresh `uid`, `lastUpdated`, `indexedNodes` and `reindexCompletionTimestamp` — and the suggester schedule.
8. Worked example: every field Oak writes for one `nt:file` node with a `jcr:content` child under the fixture's default definition, with each field's kind, options, norms, doc-value type and value transformation. The example lists `full::nodeName` and both `:fulltext` node-name values.
9. An "AEM safety invariants" section, and the `docs/analysis/README.md` rows for this document and for `lucene-oak-analysis.md`, which task 1002 writes while leaving the README to this task.
