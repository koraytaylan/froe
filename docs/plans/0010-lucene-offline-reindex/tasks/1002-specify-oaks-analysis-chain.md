# Specify Oak's Analysis Chain And Numeric Encodings

Write `docs/analysis/lucene-oak-analysis.md` from two sources: the `lucene-core` that `oak-lucene` vendors, for the numeric token streams, the prefix coding, the long, integer and double field types and what the 4.7 match version selects; and `lucene-analyzers-common` 4.7.2 — not vendored by Oak, so the document pins the Maven artifact `org.apache.lucene:lucene-analyzers-common:4.7.2:sources` by SHA-256 and records how it was obtained — for the standard tokenizer and its JFlex-generated scanner with that scanner's Unicode version, the lower-case filter and the version-dependent character utilities behind it, the word delimiter filter and its iterator, the shingle filter and its analyzer wrapper, the path-hierarchy tokenizer, the character-tokenizer base, and the token-count-limiting analyzer and filter. Also Oak's own analyzer; the per-field analyzer the Lucene definition builds, which routes `:ancestors` through a path-hierarchy chain when `evaluatePathRestrictions` is on and is wrapped in the token-count cap at `maxFieldLength`, default 10,000, not wrapped at all when `maxFieldLength` is negative, and wrapped at zero — where the limiting filter refuses a limit below 1, which Oak's fulltext editor catches per document, dropping every document with an analyzed field, so froe refuses a definition with `maxFieldLength = 0` by name in task 1005, there being no token stream to reproduce; the newline-only tokenizer Oak's suggest helper supplies; and the writer configuration Oak builds, which keeps the definition's analyzer as the *default* of a second per-field wrapper whose per-field entries bypass the token-count cap: `:spellcheck` gets Oak's shared analyzer instance under a shingle wrapper at a maximum shingle size of 3 and `:suggest` gets the suggest helper's analyzer unless `suggestAnalyzed`, so those two fields are never capped. The document also pins, by URL and SHA-256, every Unicode Character Database file the tokenizer's tables are generated from — `WordBreakProperty.txt`, `Scripts.txt`, `LineBreak.txt`, `Blocks.txt` and `UnicodeData.txt` — for the Unicode version the pinned grammar names in its `%unicode` directive, since the 4.7 grammar's character classes reference `Word_Break`, `Script`, `Line_Break`, `Block` and `General_Category` properties. The `docs/analysis/README.md` row lands with task 1001, which owns the README.

**Steps:**

1. The standard tokenizer: the UAX#29 word-break rules as the 4.7 grammar implements them, every token type — `<ALPHANUM>`, `<NUM>`, `<IDEOGRAPHIC>`, `<HIRAGANA>`, `<KATAKANA>`, `<HANGUL>`, `<SOUTHEAST_ASIAN>` — with the exact `\p{…}` character classes the grammar assigns it, the maximum token length of 255, offsets and the position increment of skipped tokens; the Unicode version quoted from the pinned grammar's own `%unicode` directive, the scanner the tokenizer selects at match version 4.7, and the pinned Unicode Character Database files of that version.
2. The lower-case filter: at match version 4.7 it lower-cases per code point through the running JVM's own case mapping — state that the consumer's tables are Temurin 21's and that froe's case table is enumerated from the image's JVM by the judge in task 1003, the consumer's own truth.
3. The word delimiter filter with Oak's flags: the default character-type table its iterator classifies code points with and how that table is derived, splits only at delimiter characters — no case-change split, since the input is already lower-cased by the preceding filter and Oak does not set the split-on-case-change flag, and no letter–digit split, Oak not setting the split-on-numerics flag either — English possessive stripping, sub-word position increments and offsets, and the preserve-original variant `analyzers/@indexOriginalTerm` selects, which emits the undelimited original term beside the generated parts.
4. The shingle filter at a maximum shingle size of 3: unigram output, the `_` filler, the space separator, position increments and the token type it sets.
5. The path-hierarchy tokenizer with its default delimiter and skip: one token per ancestor path with the offsets and position increments it emits, and the fact that `:ancestors` is an analyzed field over the node's *parent* path, so for `/content/interop/page` its terms are `/content` and `/content/interop`, not the standard tokenizer's `content`, `interop`. Then the suggest tokenizer, a character tokenizer splitting on newlines and, like every character tokenizer, at a maximum word length of 255 UTF-16 code units, checked after each code point is appended, so a token ending in a surrogate pair reaches 256 units and a suggest value above 255 code units yields several terms. Then the token-count cap — applied per field value, since Lucene's own inverter opens one token stream per field instance and Oak adds one field per property value — what it does to offsets and positions at the limit, and its behaviour at zero; the two fields the cap never reaches; and how several values of one field compose, as Lucene's own inverter composes them: after each value's tokens the end state's position increment and end offset are added, then the position-increment gap of 0 and the offset gap of 1. That makes each chain's end state part of the specification, stated per chain, capped and uncapped — the standard tokenizer's final offset is the scanned length and its final increment counts skipped positions, while the shingle, path-hierarchy, suggest and capped chains each have their own.
6. Numerics: the prefix coding of a long and of an integer, the sortable-long encoding of a double, the precision steps the long, integer and double field types use in 4.7, read from Lucene's default precision step and from the field types rather than assumed, the numeric token stream's attributes, and how each shift level becomes a term at the same position with `DOCS_ONLY`.
7. Worked examples with expected token tuples for a mixed-case, hyphenated, possessive, digit-bearing string under each analyzer, and for a path under the path-hierarchy chain, to be confirmed by task 1003's vectors.

- **Done when:** the document exists with every filter's behaviour naming the Java file and method it was read from, both artifacts' provenance, the analyzers-common checksum and every Unicode Character Database file's checksum are recorded, and every worked example carries its expected token tuples; their confirmation against the judge's `analyze` output is task 1003's acceptance, `git diff --check` is clean, and the commit body records the omitted gates.
