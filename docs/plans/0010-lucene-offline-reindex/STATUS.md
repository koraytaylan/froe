# Plan 0010 — Lucene Offline Reindex — 🚧 In progress

The roll-up row in [../STATUS.md](../STATUS.md) must stay in sync with this file. Task-level truth lives in [tasks/](tasks/) frontmatter; Makina's integration coordinator updates both layers.

- **Status:** 🚧 In progress.
- **Goal:** `froe index reindex` rebuilds Lucene definitions natively with Oak's document model, analyzer chain and numeric encodings reproduced exactly, installs the result with plan 0008's transport and bookkeeping, and a real Oak serves the same query results through it as through its own index.
- **Root cause:** plan 0009 writes valid indexes; only Oak's document semantics make them the indexes Oak expects, and those semantics — rules, analyzers, field types — are spread over `oak-search`, `oak-lucene` and `lucene-analyzers-common`.
- **Approach:** two specifications (documents, analysis), analyzers proved token-by-token against the image's classes, numeric encodings pinned by vectors, a document maker ported from Oak's own with typed refusals for unsupported features, the reindex operation on the established skeleton, the command's flags and documentation, an interop phase whose oracle is Oak's own reindex compared by enumeration plus live queries, and a frozen review; only fulltext-enabled definitions, the ones Oak writes with `oakCodec`, are in scope.
- **Progress:** 10/11 tasks done; 0 blocked; 0 dropped.
- **Integration:** `planned`; run —; base `develop` @ `314b9c704fef73636d40f3e7ec5ff2c839aa1870` plus plans 0006–0009 merged; validation base —; mode —; final integration —.
- **Exceptions:** Task 1002 found that the token-count filter's refusal of a limit below one, which its own text and task 1005's rely on, is a **later Lucene's** behaviour: in the pinned 4.7.2 a `maxFieldLength` of 0 silently empties every analyzed field. froe still refuses such a definition, but as its own choice rather than as a reproduction of an Oak refusal. (Coordinator-owned blocked/dropped reasons are recorded here.) Task 1003 found three more, each from the pinned sources and each confirmed by Oak's own analyzers: the word rule's longest match is not the greedy walk of its alternatives (`docs/analysis/lucene-oak-analysis.md` §2.4), the token-count cap **does** change a stream's end state because it stops pulling rather than draining (§7), and `CharTokenizer`'s final offset is the whole value rather than the last token's end (§7). Task 1004 found that Oak's DATE conversion runs through Jackrabbit's `ISO8601` rather than any ISO-8601 parser, needing its own pinned artifact (`docs/analysis/lucene-oak-analysis.md` §0.4) and its own specification section (§8.4) before the code; sharing that parser with the version-storage planner makes the planner stricter, which is the direction it already documents as failing closed. Task 1005 corrected two more statements of `docs/analysis/lucene-oak-documents.md` against the source — `fulltextEnabled` excludes `useInSuggest` and `useInSpellcheck`, and a duplicate property definition leaves the first or the second depending on whether the collision is between the children's own names or between their `name` properties — and split its tests at the seam the thousand-line gate found, so the name patterns are replayed in `lucene_name_pattern_tests.rs` and the rules in `lucene_rules_tests.rs`. Task 1006 made the definition-level `valueRegex` a refusal rather than a carried field — it gates the per-property fulltext loop with `Matcher.find`, and froe evaluates no value regular expression — and split its golden cases into `tests/lucene_documents/` when the thousand-line gate found the seam. Task 1007 recorded two guards as defence in depth rather than as directly neutralizable — the by-name `:data` copy, which the read-back verification catches first, and the fresh segment directory, which plan 0007's residue refusal makes unreachable — and moved the Lucene fault fixture into `fault_injection/lucene_fixture.rs` when the thousand-line gate found the seam in `test_support.rs`. Task 1009's oracle found **four** defects, three of them outside this plan's own range and one of them shipped. (1) `RecordWriter::write_node` wrote a node's template property names in whatever order its caller passed while Oak's own `getProperties` pairs the *i*-th of the names its `Template` constructor **sorts** with the *i*-th value slot, so every definition `rewrite_node_with_edits` rewrote read back in Oak with each value against the wrong name — a `STRING` where Oak expects a `LONG`, a single value decoded as a list of twenty million elements — while froe's own reader, pairing stored position with stored position, could not see it. The sort is now enforced in `write_node` itself, `docs/storage-format.md` §4 records why the order is load-bearing, and a unit test asserts the stored name order with the neutralization to match. (2) That defect is also what commit `c7cd9c3`'s measurement was made of: a counter on an unresolvable lane was refused because Oak's lane "never completes a cycle", and the lane in fact failed its conflict merge on the definition froe had deformed. With the writer corrected Oak rebuilds on the first cycle, so the refusal is **reverted** and the counter is reset again — `property_reindex`'s scenario now ends in Oak's own from-scratch rebuild, 37 entries, all canonical. (3) `indexAnalyzedProperty` writes an untokenized `StringField` — `DOCS_ONLY`, unstored whatever `useInExcerpt` says — for a **regular-expression** property definition whose name is one of `IndexHelper.NOT_TOKENIZED`; every `jcr:uuid` in a Sling repository reaches the fixture's catch-all pattern, so Oak's own rebuild differed on `full:jcr:uuid` at the first comparison (`docs/analysis/lucene-oak-documents.md` §3.3). (4) `NodeStateFacetsConfig` persists a child **only** for a multi-valued dimension, and one per path element rather than for the last alone; froe wrote one per dimension whatever its arity, which Oak's own empty `facets` node on the fixture contradicted (§5.3). Task 1009 also re-keys both enumerations by each document's own `:path` before comparing, because Lucene's document numbers record the order a writer added documents in — Oak's editor takes it from a node's map order and froe's walk takes it sorted — and no query can observe it.

- **Outcome:** `froe index reindex` rebuilds Lucene indexes natively — Oak's document model, analyzer chain and numeric encodings reproduced exactly — and Oak serves the same query results from the froe-built index as from its own.
