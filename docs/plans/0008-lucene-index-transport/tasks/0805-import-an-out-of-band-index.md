# Import An Out-Of-Band Lucene Index

Implement the import under the same skeleton as the reindex. `plan_lucene_import(directory, input, options: &LuceneImportOptions) -> LuceneImportPlan` validates the input directory: `indexer-info.properties` with its checkpoint, every local index directory with its `index-details.txt` (a directory whose `indexPath` is not a Lucene definition in the store is refused at plan time, naming the directory and its path — adding a definition is oak-run's job), every directory's segments and headers, and `index-definitions.json`, read back through a bounded reader (`definitions_json_reader.rs`, the stub plan 0006 left: the grammar task 0610's renderer emits, decoded back — the type codes, the `str:` escape, `[0]:<Type>` empty typed arrays and base64 binaries — with sizes validated before allocation and typed errors naming the offset). The file is never byte-compared with the store, because oak-run prints the lane-switched, already-reindexed *copy* of the definition — `reindexCount` one above the store's, `refresh = true` from the lane revert, a `seed` if the run created one, and the copy's `:status` — so the comparison is the one Oak itself uses for drift, the one its Lucene index-information provider performs over visible clones, which keep hidden properties and drop hidden child nodes (plan 0006's `definition_drift`: `reindex`, `reindexCount` and every hidden property name ignored, as that comparison's own ignore rule ignores them; a visible child added or removed counted), extended with the ignore set `{refresh, seed, corrupt, indexImportState}` — a set of names is all plan 0006's comparison takes — after which this task asserts the five directions itself, since the tolerances are directional and a symmetric ignore would excuse real drift: `refresh` tolerated only on the file's side, `seed` only when the store lacks it, `corrupt` and `indexImportState` only when the store has them and the file does not, and a `facets` visible child only when the file has it and the store does not, since an out-of-band build's document maker persists it. The last is directional and must be keyed on the store, which is what governs it: when the store has no `facets` child, drop it from the file's side before the comparison; otherwise drop it from neither. Two equal children then compare equal, two differing children are drift, and a store-only child is the removed visible child it is. Dropping it unconditionally from the file's side would manufacture a removed visible child in the ordinary case, where both sides carry it — Oak creates that child the moment any facet configuration is built, and the dump keeps visible children — and two equal `facets` children are no difference to the comparison, whose ignore set governs property names at every depth while a child present on both sides falls through to that same filtered comparison, applied recursively. A `seed` present on both sides and differing is drift, refused, and has its own named test. The copy's reindex cleared `corrupt` and removed `indexImportState`, a corrupt-flagged index being the usual reason for an out-of-band build; drift is evaluated only for the selected definitions that have an index directory in the input, and other keys in the file are ignored as oak-run's importer ignores them; any remaining difference is definition drift, refused with the first differing property or child named and the operator pointed at oak-run and AEM for definition changes. Every selected definition must be asynchronous; a synchronous one is refused by name with the reason the architecture gives, and so is a hybrid one — a property definition with `sync` or `unique`, or a `nodeTypeIndex` rule with `sync`, the test `docs/analysis/index-definitions.md` records — because Oak keeps its synchronous property index in the hidden child `:property-index`, which its own synchronous editor creates and flags `retainNodeInReindex`, and froe builds none; with hybrids refused, the retain rule of task 0706's rewrite never fires on an import, since `:property-index` is the only hidden child Oak ever flags. The state rule is evaluated per selected definition against the directory's one checkpoint, and the directory is refused naming every definition the checkpoint does not fit. `PreparedLuceneImport::prepare` repeats it all under the lock with plan 0007's protocol (the shape check and the two pre-lock apply-identity gates, lock, both again, replan, fingerprint, certified archive number, the metadata-source gate); `apply` rechecks the fingerprint and the path identity and opens the store through `WritableRepository::open_prepared`. `apply` writes, per definition: the mapped directories through `OakDirectoryWriter` (each `dir.<name>` mapping to its hidden child; a mapping to `:suggest-data` or its mount-decorated name is skipped with a plan line — a recorded departure from oak-run's Lucene importer, which copies it — and any other mapping the definition does not know is refused), the bookkeeping oak-run performs — `:status` replaced with a node carrying `uid` alone — a `STRING` of decimal epoch milliseconds, distinct from the previous value, read back strictly (oak-run's Lucene importer removes the node and Oak's fulltext editor writes the `uid` in its place); the other three properties task 0601 records on a `:status` node, `lastUpdated`, `indexedNodes` and `reindexCompletionTimestamp`, are deliberately absent, since Oak's importer leaves no post-import state to copy them from — a departure recorded at the site and visible to `froe index list` and to Oak's own printer, `:version` from the fresh-index format-version rule, `:index-definition` replaced by the visible-state clone (as the importer's definition-refresh step replaces it), `reindex=false`, `corrupt` and `indexImportState` removed (as Oak's own cycle clears the one and that refresh step removes the other; Oak's importer installs the file's node wholesale and removes `indexImportState` itself in its final step), the hidden `:disableIndexesOnNextCycle` set under the disabler's predicate as the importer's data step sets it, and `reindexCount` set to the file's value (0 when absent, as Oak's own increment reads it) plus one — all composed into task 0706's `DefinitionEdits` (`ReindexCount::Set`, the property replacements and removals, the new hidden children) so the definition is rewritten once under one identity discipline — which is what the importer's data step produces after Oak's own definition updater installed the file's value (one above the store for froe's own dump, two above for an oak-run build); the file's `refresh` is not copied, since froe refreshes the stored definition by cloning it, a deviation recorded at the site — the pre-existing hidden children dropped as that updater drops them when it installs the file's node wholesale — then the spine rewrite, read-back verification of every file through the open session before anything is published, one head move, a fresh reopen, and the typed `LuceneImportOutcome`. No checkpoint is released: the only checkpoint the rule accepts is the lane's, which the lane owns (a recorded departure from oak-run's importer, whose fourth step releases it). `:suggest-data` is never imported; its absence is a departure from oak-run's Lucene importer, which copies it, recorded at the site and safe because Oak's own Lucene writer rebuilds the suggestions whenever their `lastUpdated` is missing.
