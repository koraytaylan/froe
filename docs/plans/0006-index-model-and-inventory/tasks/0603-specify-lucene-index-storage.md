# Specify Lucene Index Storage In The Repository

Write `docs/analysis/index-lucene-storage.md`: how a Lucene index directory is stored as repository content, how Oak reads it back, and the filesystem layouts oak-run uses to move it in and out. This is the reader specification for plan 0006, the writer specification for plan 0008's importer, and the storage target for plan 0010's native reindex. It deliberately stops at the file boundary: the bytes *inside* an index file are the Lucene 4.7.2 format, whose table of contents plan 0008 specifies as a section of this document before reading it and whose write side plan 0009 specifies in full.

**Steps:**

1. Record the directory node: `:data` and `:suggest-data` under the definition, and the mount-decorated names `:<mount>-index-data` and `:<mount>-suggest-data`; the `dirListing` property, written on close when `saveDirectoryListing` is enabled and the file set changed since the directory was opened, and read in preference to the child names only under that same setting, which defaults to true, so a stale `dirListing` under `saveDirectoryListing=false` is ignored by Oak; that property's stored order, which is neither sorted nor insertion order because the writer holds the names in a concurrent hash set, and which Oak therefore reads as a set; and `unsafeForActiveDeletion` — a *file-node* property the directory writes only when the blob-deletion callback reports active deletion unsafe, never for an inline blob.
2. Record the file node: `uniqueKey`, sixteen random bytes written as thirty-two lower-case hexadecimal characters when the file is created; `blobSize`, written from the definition's value, which defaults to `1024 * 1024 - 1024` and is clamped to at least 1024, and read back from the file node itself, where the fallback for a node without the property is the buffered reader's own default of `32 * 1024` rather than the definition's; `jcr:lastModified`, the wall-clock time at flush; and `jcr:data`.
3. Record both `jcr:data` encodings and the dispatch between them: a single `BINARY` reads as streaming, anything else reads as buffered, and a buffered file whose `jcr:data` is not `BINARIES` reads as zero-length, Oak never erroring on the type. The streaming form is one blob with the unique key appended once, its length the blob length minus the key length, never below zero. The buffered form is `blobSize` chunks, each with the unique key appended, its length `count * blobSize - (blobSize - last.length()) - key length`, and loading a chunk reads only `min(blobSize, length - i * blobSize)` bytes of it. State that an absent `uniqueKey` is tolerated by both readers, which read the key as null and subtract no length, so froe treats it as length-neutral rather than as a defect. State which writer produces which: the directory Oak's Lucene editor opens writes streaming files, because `oak.lucene.enableSingleBlobIndexFiles` defaults to true, and that is the shape the real 1.90.0 fixture holds, while Oak's own Lucene importer copies a directory without streaming and so produces buffered files.
4. Record what the blobs are in a segment store: the directory's blob factory stores through the node builder, so every chunk is an ordinary inline binary value record with a block list over bulk segments, addressed exactly as `docs/analysis/record-layer.md` already specifies; froe's `read_binary_stream` reads them.
5. Record the consistency check oak-run's level 1 performs — every binary property under the definition subtree streamed to its end, the streamed byte count compared with the blob's reported length — and what level 2 adds: a copy to a local filesystem directory, Lucene's own index check over that copy, and a document count read back from it. `froe index check` can then state exactly which level it implements.
6. Record the dump layout: an index folder's base name is up to three trailing path elements with `oak:index` dropped, joined by `_`, with non-word characters stripped and a cap of 127 characters; an existing local directory whose `index-details.txt` names the same `indexPath` is reused before a new one is made, and a name collision otherwise appends `_0`, `_1` and so on; the per-index subdirectory name strips colons; and `index-details.txt` is written beside the files. Record the import layout: `indexer-info.properties` is read from the root directory the importer is handed, whose direct subdirectories are then scanned for `index-details.txt`, each match becoming one local index directory whose filesystem names map back to JCR names; and Oak's Lucene importer removes `:status`, applies the stored definition from the updated state, and removes and rewrites each mapped directory.
7. Record the status and definition bookkeeping the Lucene editor performs beyond the generic index update: `seed` and the stored definition written when the editor context builds its definition; `lastUpdated`, `indexedNodes` and `reindexCompletionTimestamp` written when the writer closes; an empty index persisted on a reindex that indexed nothing; and the suggester's `:suggest-data/lastUpdated`.
8. Worked example: the fixture's `/oak:index/lucene/:data/_1.si` node — `blobSize` 1,047,552, a 32-character `uniqueKey`, a single `Binary` of 241 bytes reporting a file length of 225 — derived from the rules the document states.
9. Add the "AEM safety invariants" section: a file node with a wrong length makes Oak throw on open, an absent unique key is read as no trailing key, the `dirListing` must agree with the children whenever `saveDirectoryListing` is on, and `:suggest-data` may be absent because Oak's writer rebuilds the suggestions whenever their `lastUpdated` is missing. The `docs/analysis/README.md` row for this document lands with task 0601, which owns the README.
