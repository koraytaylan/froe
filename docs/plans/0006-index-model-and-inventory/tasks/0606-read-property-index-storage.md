# Read Property And Unique Index Storage

Implement the read side of the property family: key derivation exactly as `docs/analysis/index-property-storage.md` specifies it, enumeration of a mirror index (`:index/<key>/<path…>` with `match`) and of a unique index (`entry` arrays), the `TypePredicate` over `/jcr:system/jcr:nodeTypes`, and a structural consistency check that is froe's contribution beyond oak-run: for every indexed entry, the content node exists and carries the key value under one of the definition's property names, and for every node the definition covers, the entry exists. Enumeration is streaming and depth-bounded like every other walk in the crate, with an exact set of records on the path refusing cycles.

**Steps:**

1. `key_encoding.rs`: `keys_for_property(values, pattern) -> Result<BTreeSet<String>>`, fallible because the value-pattern test is — a regular-expression pattern answers with the typed `Unsupported` error task 0605 defines, which this function propagates rather than swallowing, since the scope forbids reinterpreting one silently — composing the value-pattern read, the empty token, the 100-unit truncation and `java::url_encode`, with set semantics because Oak's own encoder yields a set and the editor unions the keys of every value — two values that collapse to one key (both empty, or a shared 100-unit prefix) produce one entry, and a unique index built from them must not be refused as a duplicate; unit tests for the empty string, a 101-unit value, a value truncated inside a surrogate pair, two values collapsing to one key, a multi-valued property, and a binary property contributing nothing.
2. `type_predicate.rs`: `TypePredicate::new(root, declared_names)` reading `rep:primarySubtypes`, `jcr:isMixin` and `rep:mixinSubtypes` lazily, and `test(node)` over `jcr:primaryType` (read strictly, so a single `NAME` only) and `jcr:mixinTypes` (read strictly, so `NAMES` only); the caller derives `declared_names` from `declaringNodeTypes` with the same `NAMES`-only rule, so a definition whose `declaringNodeTypes` is stored as strings yields a predicate that matches nothing, as Oak's does; tests over a synthetic `jcr:nodeTypes` tree that pins the asymmetry (a declared mixin matches its mixin subtypes; a declared primary type does not match mixin subtypes) and the non-`NAMES` case.
3. `mirror.rs`: `MirrorIndex::entries()` yielding `(key, path)` for every `match=true` node sorted by `(key, path elements)`, elements compared as byte strings — the order plan 0007's builder requires, which differs from a plain name sort whenever one indexed path is a strict prefix of another, `count_for_key`, and the reference-index flavour where keys are identifiers and paths are property paths; at the key level of `:index` (and `:references`/`:weakreferences`) every child is a key whatever its name — Oak's empty-value key is the hidden name `:`, the empty token, and every other key is URL-encoded — and only below the key level, where names are content path elements, are hidden children and hidden properties skipped as Oak's visible editor skips them, except the `:count_*` properties, which are counted and reported rather than treated as content. A reference index whose hidden child is absent enumerates as empty, because Oak creates `:references` and `:weakreferences` only on the first insert.
4. `unique.rs`: `UniqueIndex::entries()` yielding `(key, paths)` and flagging any `entry` with more than one element as a duplicate state; which reader applies to a definition follows task 0605's strategy verdict (a `BOOLEAN` `unique = true`, nothing else).
5. `consistency.rs` inside `property/`: `check_entries(provider: &dyn SegmentProvider, root, definition, budget: EntryCheckBudget) -> PropertyIndexReport`, the entry half alone: for mirror and unique definitions every entry's path resolves in the state root and carries the key under one of the definition's property names, and for a reference definition, whose keys are unencoded identifiers and whose values are relative property paths, the path resolves against the state root and that property's values contain the identifier. Its budget is charged per entry, and it is the pass plan 0007's publication tail runs. Beside it, `check(provider: &dyn SegmentProvider, root, definition, budget: NodeCheckBudget) -> PropertyIndexReport` runs that half and then the covered-node half, listing missing entries, stale entries, mismatched keys and duplicate unique entries, its budget charged per visited node. `EntryCheckBudget` and `NodeCheckBudget` are both `pub` with a private field and a named constructor taking the limit, `NodeCheckBudget` also carrying `unlimited()` for the run task 0611 describes, where no node estimate is available and a guessed number would be worse than none, as `CompactionOptions` is built — private fields, not `#[non_exhaustive]`, are what block a struct literal — and they are the crate's first public budget types, its four existing ones being crate-private, so a downstream test can set either; each carries the exact limit and limit-plus-one regression the testing standards require, and each refusal is operator-visible: task 0611 documents the `NodeCheckBudget` refusal, which `froe index check` raises, and task 0710 the `EntryCheckBudget` refusal, which the reindex's publication tail raises.
6. Add `crates/froe/tests/support/property_index_layout.rs`, registered in `crates/froe/tests/support/mod.rs` and opening with the same `#![allow(dead_code, reason = …)]` as `filesystem_snapshot.rs`, since every binary declaring `support` compiles it: an *independent* mirror- and unique-layout helper — a second, deliberately naive in-memory tree builder that emits `:index` subtrees through the independent encoder — so the reader is not checked against its own encoding; plan 0007's builder tests reuse the same helper against the writer.
7. Tests in `crates/froe/tests/property_index_reader_tests.rs` over synthetic stores whose `:index` subtrees the helper wrote (an empty-value node with its `:` key included); the binary declares `mod support;` under the crate-level `#![allow(dead_code, …)]` that `binary_stream_tests.rs` carries.

- **Done when:** each of `EntryCheckBudget` and `NodeCheckBudget` accepts at its limit and refuses at its limit plus one, and an `unlimited()` node budget completes a walk that a `NodeCheckBudget` of one fewer node than the walk visits refuses, the reader enumerates every entry the independent helper wrote, the consistency check reports each injected defect (a removed content node, a changed value, a forged `match`, a duplicate unique entry) by path and kind, and the stable host gate passes.
