# Specify Property-Family Index Storage

Write `docs/analysis/index-property-storage.md`: the exact on-repository shape of the `property`, unique, node-type, `reference` and `counter` indexes, and the exact computation that produces it, cited to the Java. Plan 0007 rebuilds these structures and proves the rebuild against Oak's own reindex; a rebuild can only be held to that standard if the specification names every byte Oak would write and every input to it.

**Steps:**

1. Record the mirror strategy's insert, remove and prune: `:index/<key>/<path elements>` with a `match` boolean on the node the indexed path addresses — the insert descends every element and sets it unconditionally, so it lands on an interior trie node whenever a shorter indexed path shares the key, and the prune keeps any node carrying `match` or a child — the root path mapping to the key node itself, and the fact that insert and remove each adjust the approximate counter on the `:index` node and on the key node, never on a path-element node. State that the editor's uniqueness check creates `:index` unconditionally, so a property index that indexes nothing still carries an empty `:index`.
2. Record the unique strategy's insert and remove: `:index/<key>` with an `entry` `String[]` holding the absolute path, multiple entries only as a transient duplicate state, and the approximate counter adjusted on the `:index` node alone — the key node carries none.
3. Record key derivation end to end: which values the editor contributes, binaries and empty properties never among them; the prefix lists read converting to `STRINGS`; the match rule, where include prefixes win, an exclude prefix matches in either direction, a regular expression applies only when no include prefix matched, and a value matching no include prefix is rejected whenever include prefixes exist and no regular expression is set; and the encoding, which is the `:` empty token for an empty value, truncation to 100 UTF-16 units, and then Java's URL encoding of the truncated value as UTF-8. State that a truncated surrogate pair encodes as `%3F`, because that is what Java's encoder does with a lone surrogate.
4. Record which properties of which nodes are indexed. `propertyNames` is read by the editor converting, a single `NAME` and a whole `NAMES` array alike, so a `STRING` value is indexed, while the query planner's strict `NAMES` read yields nothing for it — a definition Oak indexes but the property index never selects; the node-type index's own lookup instead falls back to a converting `STRINGS` read with a warning, and does select it. `declaringNodeTypes` is applied through the node-type predicate: primary subtypes come from `rep:primarySubtypes`, a mixin contributes its own name and `rep:mixinSubtypes`, and a declared name that is not a mixin matches primary types only. The path filter has three verdicts: exclude wins, include by ancestry, and traverse for an ancestor of an include. Hidden nodes and properties are invisible to indexing because every index update Oak drives is wrapped in the visible-editor filter, at all five of its sites: the reindex composite, the synchronous incremental editors, the asynchronous lane, the importer's catch-up diff and the out-of-band build. And the `nodetype` index is an ordinary property index over `jcr:primaryType` and `jcr:mixinTypes`, which Oak's initial content creates with `declaringNodeTypes` left null. Record which reads are type-strict. A strict `NAMES` read returns a value only for a multi-valued `NAMES` property — a single-valued `NAME`, a `String` and a `String[]` all read as empty — and a strict `NAME` read only for a single `NAME`, so a `declaringNodeTypes` of any other type yields a predicate that matches nothing, the node-type predicate reads `jcr:primaryType` strictly as a `NAME` and `jcr:mixinTypes` strictly as `NAMES`, and the query planner selects on `propertyNames` only for a `NAMES` value. `unique` is read strictly as a `BOOLEAN` by the editor, the lookup and the planner alike, so a `STRING` `unique = "true"` — what a Sling POST without `@TypeHint=Boolean` stores — is a *mirror* index to Oak, and the strategy chosen for it is the mirror strategy. The path filter accepts `STRING` or `STRINGS` and otherwise falls back to its defaults, and `valuePattern` is read strictly as a `STRING`. The prefix lists are read two ways: the editor's read of the builder converts an array to `STRINGS`, while the planner's and the lookup's read of the node state is strict and sees only `STRINGS`. A `NAMES`-typed `valueIncludedPrefixes` array is therefore indexed by the editor but gives the planner an empty include list, which then rejects every value — indexed but never selected, the same asymmetry as `propertyNames`. A `NAMES`-typed `valueExcludedPrefixes` array reads as an *empty exclusion* on the query side, so the planner serves the excluded values out of an index the editor never populated with them: wrong, empty results, not merely an unused index. Both readers take a single prefix value strictly as a `STRING`, so a single non-`STRING` `valueIncludedPrefixes` or `valueExcludedPrefixes` yields a null prefix the match test throws on — a definition Oak cannot index. Record that Oak's own definitions store `propertyNames` and `declaringNodeTypes` as `NAMES`.
5. Record how a value of a non-string type becomes a key string: for every type stored as its string form the conversion is the identity, and the document must say for which types — `DOUBLE`, `DECIMAL`, `DATE` — that identity holds only because Oak wrote the stored string with the same converter.
6. Record the reference index: `:references` and `:weakreferences`, the latter spelled in lower case; its editor is built with no path filter and no node-type predicate, so `includedPaths`, `excludedPaths` and `declaringNodeTypes` are ignored and only the version-store prefix test and the visible-editor wrap restrict it; keys are the referenced identifiers unencoded, and values are property paths made relative by stripping the leading `/`; strong references whose path starts with the version-store path are skipped, and because that test is a plain string prefix a sibling named `jcr:versionStorage2` is excluded too, while weak ones are never skipped; and a reindex processes every reference as an addition. State that both hidden children are created lazily — the editor memoizes the child and the mirror strategy resolves it only inside the loop over inserted keys — so a store with no weak references ends Oak's reindex with `:weakreferences` absent.
7. Record the counter index: `resolution`, default 1000, read converting to `LONG` and then narrowed to 32 bits, so a `STRING` `"500"` counts; `seed`, created as the most significant 64 bits of a random UUID and used untruncated on the run that creates it but narrowed to 32 bits sign-extended on every later run, so only those bits take part from then on; the bit mask, which is the highest set bit of `resolution` doubled and then reduced by one; the per-child SipHash chain, seeded from `seed` and extended at each step with the Java string hash code of the child name; the folding of the four state words into one 32-bit value, by exclusive-or and then `x ^ (x >>> 16)`; the test that a hash masked by the bit mask is zero, which adds the bit mask plus one to every ancestor's `:cnt`; the removal of `:cnt` when it reaches zero; and the fact that the editor returns before creating `:index` when no node hit, so a small store ends Oak's reindex with the counter definition holding no `:index` at all. Record the estimate's reading rules with the constants they actually use — the approximate counter's own resolution of 100, never the definition's `resolution`. Note the two switches that leave this path and are out of scope: `oak.countHashed=false`, which selects the unhashed editor and its matching reader, and `oak.index.useCounterOld=true`, which replaces the editor and the reader with the old counter's before the default estimate is reached. froe implements the default of both.
8. Record the approximate counter's adjust and read paths precisely enough to state the one thing froe relies on: the `:count_<uuid>` properties are randomized in name, presence and value, so no rebuild can reproduce them and a comparison against Oak must exclude them by prefix.
9. Worked example: one `sling:Folder` node under `/content/interop`, one `mix:referenceable` node, one `REFERENCE` property and one counter hit, each traced from the rules to the `:index` node it produces and checked by hand against the fixture.
10. Add the "AEM safety invariants" section. The `docs/analysis/README.md` row for this document lands with task 0601, which owns the README; this task only writes the document.

- **Done when:** `docs/analysis/index-property-storage.md` exists, every statement cites a Java file and method, and the document's worked example — one `sling:Folder` node under `/content/interop`, one `mix:referenceable` node, one `REFERENCE` property and one counter hit — is checked by hand against the real Sling fixture's `/oak:index/nodetype/:index/sling%3AFolder/content/interop`, `/oak:index/uuid/:index/<uuid>`, and `/oak:index/counter/:index` nodes, `git diff --check` is clean, and the commit body records the omitted gates.
