# Implement The Bounded External Sort For Index Entries

The `nodetype` index of an 18-million-node store produces one entry per node per type value; sorting them in memory is exactly the store-proportional residency the bounded-memory safety case forbids. Implement `SortedRuns<Record>` in a new crate-private module `froe::external_sort` at the crate root (`pub(crate) mod external_sort;` in `lib.rs`, beside `cache`, `packed_records` and `parallel`, which follow the same pattern), generic from the start over a record type that supplies its ordering, its serialized form and its resident byte cost through a `SpillRecord` trait, so that plan 0009's Lucene inversion can sort `(field, term, document)` postings through the same code without depending on the segment-store write path: records are appended into an in-memory run until a declared byte budget is reached, each full run is sorted and spilled to a file under the caller's work directory, and `into_sorted()` returns a merge iterator over the spilled runs plus the last in-memory one whose fan-in is bounded — when the run count exceeds a declared maximum (default 64), runs are merged in passes of that width into new spill files first — so the number of open files never exceeds the fan-in plus one, whatever budget the operator chose. This plan's record is the `(key, path)` byte pair compared as `(key, path elements)` — element by element as byte strings — so the consumer sees exactly the depth-first order the trie writer needs. The budget is charged against the bytes actually held, has its accounting unit documented, and has the exact limit and limit-plus-one regression the testing standards require. The module is crate-private, so its behaviour is covered by unit tests in the module, like the other crate-root helpers, with one integration test in `external_sort_tests.rs` because the public re-exports are themselves part of the contract.

**Steps:**

1. Create `crates/froe/src/external_sort.rs` (registered `pub(crate)` in `lib.rs`) with `SortedRuns::new(location: RunLocation { directory, name_prefix }, budget: SortBudget)` — `SortBudget` a cloneable handle onto one accounting total, so several instances holding it are charged against a single byte limit instead of a static split, which is what plan 0009's writer needs when its field set is discovered as documents arrive, `push(record)`, `into_sorted()`, a second read `into_sorted_passes() -> SortedPasses<Record>` — the consuming prefix, since it takes `self` as `into_sorted()` does — whose `pass(&mut self) -> SortedPass<'_, Record>` rewinds every spilled run and yields the sorted sequence again, beside the public `SortedPasses::from_sorted_records(records)` that wraps an already-sorted in-memory sequence and spills nothing — without it no downstream crate could obtain a `SortedPasses` at all, and plan 0009's doc-value and norms tests, which live in separate integration-test crates, could not call the consumers they cover, each run kept until the `SortedPasses` is dropped, so a consumer may walk the sequence more than once (plan 0009's doc-value and norms writers make a statistics pass, a missing-bitset pass and a write pass over the same input), and the `SpillRecord` trait (`Ord`, encode, decode, resident size); several instances share one directory (the reference collector's two run sets, plan 0009's postings, doc-value and norm runs), so each names its files under its own prefix; the caller supplies the run directory (task 0707's operation creates one per run and hands the same directory to every `SortedRuns` and, in plan 0010, a run location plus a segment directory inside it to the segment writer, whose spills stay in the run location), and `SortedRuns` owns only the files it writes there — the sorted iterator unlinks each spilled run when it is exhausted and every remaining run on drop, so the operation's subdirectory removal finds only what other components left; `SortedRuns` never appears in a public signature — the collectors that fill it return a public sorted iterator instead, while `RunLocation`, `SortBudget`, `SortedPasses`, the `SortedPass` its `pass()` returns and the `SpillRecord` bound its parameter carries are `pub` and re-exported as `pub use crate::external_sort::{RunLocation, SortBudget, SortedPass, SortedPasses, SpillRecord};` from `writer/index/mod.rs`, because the public `EntrySink::Runs` of task 0704 carries the first two and plan 0009's public doc-value and norms consumers take `SortedPasses` as a parameter — a `pub` function may not name a type reachable only through a `pub(crate)` module, nor a public generic carry a crate-private bound, which are rustc's warn-by-default `private_interfaces` and `private_bounds` under a `-D warnings` gate — then declare `pub mod index;` in `crates/froe/src/writer/mod.rs` and create `crates/froe/src/writer/index/mod.rs` as the module root with its doc comment, the public `IndexEntry` record (`key`, `path`, compared as `(key, path elements)`; task 0704's `SortedEntries` is the public iterator over it), and documented stubs for every file the plan's later tasks own (`property_builder`, `property_collector`, `counter_builder`, `definition_update`, `selection`, `plan`, `prepared`, `apply`), so those tasks fill files that already compile and never contend for the module root or `writer/mod.rs`; the module is public because the crate's integration tests are separate crates.
2. Spill file format: a length-prefixed sequence, written through a buffered writer and fsynced before the run is considered spilled, under froe-prefixed file names in the run directory; the residue policy (refuse or warn) belongs to the operation's plan (task 0707), which knows whether the operator named the work directory, and this module only refuses to overwrite a file that already exists.
3. Merge: a binary heap over run cursors, with the multi-pass reduction when the run count exceeds the fan-in; duplicates are preserved (the builder decides what a duplicate means); the open-file accounting and a merge-pass counter, both `#[cfg(test)] pub(crate)` rather than module-private — the shape `repository_lock/publication.rs`'s cutpoint takes, so task 0704's merge regression in `property_collector.rs` and plan 0009's writer in `inverted.rs` can both read them without editing this file and nothing in the lib-only build of the `-D warnings` gate reads an item only tests use — the counter counting the reduction passes task 0701's cost statement cites, both asserted by this module's own tests.
4. Unit tests in the module: exact-limit and limit-plus-one behaviour, an order property over random entries checked against a naive sort, a run count of one (no spill), of many, and above the fan-in (forcing a second pass, with the open-file accounting and the merge-pass counter asserted), the refusal to overwrite an existing file, the spill files gone once the iterator is dropped, three `pass()` calls on one `SortedPasses` yielding the same sequence and its files gone on drop, the same three over a `SortedPasses::from_sorted_records` sequence with no spill file created (repeated in `external_sort_tests.rs` from outside the crate, where the public re-exports are the only reachable surface), two instances in one directory under different prefixes, and a second record type (a plain byte string) proving the generic surface.

- **Done when:** `external_sort_tests.rs`, an integration test and so a separate crate, constructs `froe::writer::index::SortedPasses` through `from_sorted_records` and walks it twice, proving the visibility contract inside the range that freezes it; `into_sorted()` yields the naive order for 100,000 random entries under a budget that forces at least ten spills, a run count above the fan-in merges in more than one pass with the open-file accounting never exceeding fan-in plus one and a merge-pass counter asserting the pass count, no spill file remains in the run subdirectory after the iterator is dropped, and the stable host gate passes.
