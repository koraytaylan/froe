# Collect Property, Node-Type And Reference Entries From Content

Implement the walk that reproduces what Oak's property-index and reference-index editors observe during a reindex: a depth-first traversal of the state root with visible-editor semantics (hidden child names and hidden property names are never visited), the definition's `PathFilter` verdicts (`Exclude` prunes, `Traverse` descends without indexing, `Include` indexes), `TypePredicate` for `declaringNodeTypes` resolved against the state root's own `/jcr:system/jcr:nodeTypes` (as Oak's own cycle builds it, from the state it indexes and never from the head), and key derivation through plan 0006's `keys_for_property`. Every emitted entry goes into an `EntrySink::{Count, Runs { location: RunLocation, budget: SortBudget }}`: at plan time the sink only counts entries and their bytes (nothing is written, which the plan's read-only contract needs), and at apply time it feeds the crate-private `SortedRuns`, which the collector owns and turns into `SortedEntries`, a public iterator over the public `IndexEntry` record of task 0702, so the crate-private sort type never appears in a public signature. The reference collector walks every visible node without consulting the definition's `PathFilter` or `TypePredicate`, because Oak builds the reference index's editor with neither, and emits `(identifier, relative property path)` into two run sets that share the sink's one `SortBudget`, so a definition's residency stays within the one budget the safety case states, merged one at a time — the weak set's `into_sorted()` is not called until the strong set's iterator is exhausted and dropped, as plan 0009 merges one format at a time — so the open-file bound stays the fan-in plus one, each property's values unioned into a set before they are emitted (Oak's editor collects them into a set, so a value listed twice is one entry) — strong references whose path does not start with the string `/jcr:system/jcr:versionStorage` (the version-store test is a plain string prefix, so a sibling named `jcr:versionStorage2` is excluded too), weak references everywhere — as `docs/analysis/index-property-storage.md` records the editor's per-property rule, and reports for each set whether it received any entry, because Oak creates `:references` and `:weakreferences` only on the first insert and a run set that stayed empty must produce no hidden child. The walk carries its own heap stack and an exact set of records on the path, like every other walk in the crate.

**Steps:**

1. `PropertyCollector::collect(state_root, definition, sink: EntrySink, progress) -> CollectedEntries::{Counted { entries, bytes }, Sorted(SortedEntries)}` with the observer reporting `collecting index entries` (the collector opens the step itself) counting `WorkUnit::Nodes` visited and `sorting index entries` counting a new `WorkUnit::IndexEntries` around its call to `into_sorted()` — the one variant this plan adds to the `#[non_exhaustive]` enum in `progress.rs`, with its `plural_noun` and `singular_noun` arms — and a visited-node counter for the safety case's cost statement.
2. Key derivation per node: one set of keys per node across every name in `propertyNames` — exactly the per-node key set Oak's editor derives from the after state: `keys_for_property` over each property's string values, binaries and empty properties contributing nothing, unioned into one `BTreeSet` — one entry per distinct key, the node's absolute path as the value, so `(key, path)` records are distinct by construction and the builders rely on it.
3. `ReferenceCollector::collect(state_root, sink: EntrySink, progress) -> CollectedReferences::{Counted { strong, weak, bytes }, Sorted(SortedReferenceSets)}` — `SortedReferenceSets` handing out `strong()` and then `weak()`, the second merge starting only once the first iterator is dropped, which is what keeps the open-file bound at the fan-in plus one, pinned by an in-crate `#[cfg(test)]` regression in `property_collector.rs` over a store forcing spills in both sets — the accounting task 0702 exposes is crate-internal, so the test sits beside it rather than in this task's integration file, as task 0707 places its gate-seam test — with the version-storage prefix exclusion and both reference types, keys unencoded, paths made relative by stripping the leading `/`, and the per-set emptiness verdict.
4. Tests over synthetic stores: hidden nodes and properties are not indexed; a node whose two indexed properties share one value contributes one entry (Oak's per-node key set); a `Traverse` ancestor is descended but not indexed; a declared mixin matches its subtypes; a `REFERENCE` under version storage is skipped while a `WEAKREFERENCE` there is kept, and a `REFERENCE` under a sibling whose name merely starts with `jcr:versionStorage` is skipped as Oak skips it; a store with strong references only reports the weak set empty; a reference definition carrying `includedPaths` still indexes references outside the include; a multi-valued reference property listing one identifier twice yields one entry; an independent oracle — a second, naive walk in the test — produces the same entry multiset; and a store with a spliced self-reference at the closing record is refused by the collector's cycle bound.

- **Done when:** every test's collected multiset equals the oracle's, the counting sink reports the same entry count as the sorted sink for every fixture, the visited-node counter equals the number of nodes the oracle walked, the collector's cycle refusal fires on a spliced self-reference at the closing record, and the stable host gate passes.
