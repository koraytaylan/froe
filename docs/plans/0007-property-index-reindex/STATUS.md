# Plan 0007 — Property Index Reindex — 🚧 In progress

The roll-up row in [../STATUS.md](../STATUS.md) must stay in sync with this file. Task-level truth lives in [tasks/](tasks/) frontmatter; Makina's integration coordinator updates both layers.

- **Status:** 🚧 In progress.
- **Goal:** `froe index reindex` rebuilds property, unique, node-type, reference and counter indexes offline from the state Oak's own editors would index, in one head move under the lock, with a safety case, fault coverage and Oak-side proof.
- **Root cause:** Oak rebuilds a flagged property index synchronously inside the first commit after startup and has no offline path that writes the result back; on large stores that blocks AEM for hours.
- **Approach:** safety case first; bounded external sort and a streaming trie writer; Oak's exact key derivation and bookkeeping from plan 0006's specification; one compare-and-set; fresh-reopen verification; an interop phase whose oracle is Oak's own reindex of the same store, compared with only the randomized approximate counters excused; frozen adversarial review before the beta framing is lifted.
- **Progress:** 14/15 tasks done; 1 awaiting the maintainer's gate; 0 dropped.
- **Integration:** `planned`; run —; base `develop` @ `314b9c704fef73636d40f3e7ec5ff2c839aa1870` plus plan 0006 merged; validation base —; mode —; final integration —.
- **Exceptions:** 0714 is `gated: true` and its gate is **open**. Its review work is done and committed — four adversarial lenses (two found real defects, both fixed), the verification report with the five separations, the interoperability record and the known gaps — but the freeze itself, and lifting the beta framing from `docs/index.md` §5 and the feature map's two rows, is the maintainer's decision and should not be taken while the interoperability record has an open half. 0712's oracle comparison ran and passed — Oak rebuilt all 23 property-family definitions in the fixture and froe's rebuild of the same extracted bytes rendered identically for every one, the content digest differing only inside the declared `/oak:index` scope (39 lines over 52,252 nodes) and `froe check` passing — reproduced across four runs. Its **query-level comparison and counter-reset scenario have since run, during plan 0008's work, and each found a defect in this plan's own code.** (1) The rebuild wrote no `:count_*` approximate counters. Oak reads their absence without complaint and then **stops choosing the index**: over Oak's own rebuild of the fixture it planned `property uuid … estimatedCost: 3102.0`, and over froe's rebuild of the same entries it planned `traverse allNodes (warning: slow)`. The deliberate omission recorded at `property_builder.rs` was right that no rebuild can reproduce the bytes and wrong that the absence is harmless. froe now runs `ApproximateCounter.adjustCountSync` with its own entropy, and every comparison of two rebuilds excludes the prefix, as `index-property-storage.md` §11 says one must. (2) `DefinitionEdits::reset` removed a counter's hidden children without raising `reindex`. `IndexUpdate.shouldReindex`'s other trigger needs the definition to be *absent* from the before state, which a definition the store already holds never is — so Oak never even attempted a rebuild. The reset now raises the flag, and Oak logs `Reindexing will be performed for following indexes: [/oak:index/counter]` and processes its 32 entries. The flag turned out to be necessary and, on the measurements then available, not sufficient: a counter on an unresolvable lane was **refused by name** rather than reset, on three variants that all ended with the counter empty and no index on that lane committed (the reference left dangling: 129 lost-checkpoint errors and 129 reindex attempts; `/:async/<lane>` cleared: 0 and 59; that plus `async-temp` cleared: 0 and 59), while a healthy lane rebuilt every definition on the first cycle. **Plan 0010's task 1009 found that measurement to be a symptom of a froe defect and reverted the refusal.** Every one of those runs was on a store whose definition froe had rewritten with its properties out of the order Oak's own `Template` sorts into (`docs/storage-format.md` §4): Oak's conflict merge on the lost-checkpoint cycle read each value against the wrong name, threw, and failed the lane's commit — for the counter and for every other index on it, which is exactly the symptom recorded above. With the writer corrected the counter is reset again and the interop suite's `property_reindex` scenario ends in Oak's own from-scratch rebuild, 37 entries, all canonical. `ResetForReplay`, `DefinitionReport::Reset` and `DefinitionEdits::reset` therefore have producers again — the counter and, from plan 0010, a Lucene definition — and the maintainer decision about removing them is moot. Documented in `docs/index.md` §5.7 and §5.9, including that the behaviour changed twice. Four bugs in the phase itself were fixed alongside, each unexercised until now: a digest asserted to exit 0 on a store the scenario had deliberately made dangling, a wait threshold one too low, a wait deadline too short for a lane rebuilding from scratch, and a query comparison that counted Sling's own instance-keyed `/var` discovery nodes as index content. The phase completes in one run on this host, and so does the whole chain: on 2026-09-15 it ran in 198 seconds inside a chain that reached `all interop phases passed` in 905. The earlier note that a memory watchdog killed it during the 23-definition digest loop did not reproduce; see plan 0006's own status for what the interruptions more probably were. 0707 split `apply.rs` twice rather than once — into `apply/verification.rs` as well as the `apply/tests.rs` the safety case sanctions — because the operation and its verification tail together exceed the thousand-line gate, and 0708 adds cutpoints to `apply.rs` on top. 0707 also edited two files under `writer/maintenance/` that the safety case assigns to 0715: `gate_observation` was left module-private and `validate_metadata_source_apply_identity` never recorded its own call, so the wiring test 0707 owes could not be written without closing both. (Coordinator-owned blocked/dropped reasons are recorded here.)
