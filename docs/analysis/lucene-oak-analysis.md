# Oak's analysis chain and numeric encodings

What a string becomes on its way from a property value to the terms Oak
writes, and what a number becomes. Everything below is read from source at
a pinned revision: Oak's own at the pinned commit, the Lucene `lucene-core`
that `oak-lucene` vendors at that commit, and — for the analyzers, which
Oak does *not* vendor — the published `lucene-analyzers-common` artifact
pinned by checksum below.

froe reproduces this chain because a term Oak's query side looks up must be
the term froe's writer wrote. A tokenizer that agrees "usually" produces an
index that answers most queries, which is worse than one that answers none.

### 0.3 The Unicode Character Database the tokenizer's tables come from

The standard tokenizer's scanner is generated by JFlex from
`analysis/standard/StandardTokenizerImpl.jflex`, whose first directive is
its Unicode version:

```
%unicode 6.3
```

Its character classes name the `Word_Break`, `Script`, `Line_Break`,
`Block` and `General_Category` properties, so the tables are those five
files of **Unicode 6.3.0**:

| File | URL under `https://www.unicode.org/Public/6.3.0/ucd/` | sha256 |
| --- | --- | --- |
| `WordBreakProperty.txt` | `auxiliary/WordBreakProperty.txt` | `4cfdfad5a6bda872f9f3de3dba01896c8d05dda65646d83f3793ac05729734fb` |
| `Scripts.txt` | `Scripts.txt` | `3996337cf6bcf9134a3f0826d82c16e873558f0d020a1799450ceb3edc549651` |
| `LineBreak.txt` | `LineBreak.txt` | `6a38069025127a60f4a809e788fbbd1bb6b95ac8d1bd62e6a78d7870357f3486` |
| `Blocks.txt` | `Blocks.txt` | `f0c573bbcc71fcbdab285e4390f49bf711e66bf502d18d8b8c303eaf47661027` |
| `UnicodeData.txt` | `UnicodeData.txt` | `3f76924f0410ca8ae0e9b5c59bd1ba03196293c32616204b393300f091f52013` |

**Unicode 6.3.0, not the running JVM's Unicode version.** The scanner's

later Unicode does not change a single token. The *case* tables are the
opposite — §3 — and the two must not be conflated.

## 1. Oak's own analyzer

`plugins/index/lucene/OakAnalyzer.java`:

```java
protected TokenStreamComponents createComponents(final String fieldName, final Reader reader) {
  StandardTokenizer src = new StandardTokenizer(matchVersion, reader);
  TokenStream tok = new LowerCaseFilter(matchVersion, src);
  tok = new WordDelimiterFilter(tok,
          WordDelimiterFilter.GENERATE_WORD_PARTS
                  | WordDelimiterFilter.STEM_ENGLISH_POSSESSIVE
                  | preserveOriginal
                  | WordDelimiterFilter.GENERATE_NUMBER_PARTS, null);
  return new TokenStreamComponents(src, tok);
}
```

Three stages, in this order: **standard tokenizer**, **lower-case filter**,
**word delimiter filter**. `preserveOriginal` is
`WordDelimiterFilter.PRESERVE_ORIGINAL` when the definition sets
`analyzers/@indexOriginalTerm` and `0` otherwise; the protected-word set is
`null`.

`matchVersion` is `Version.LUCENE_47` throughout — `LuceneIndexConstants`
declares the shared instance `ANALYZER = new OakAnalyzer(VERSION)` with
`VERSION = Version.LUCENE_47`.

**Four flags Oak does not set, and each is load-bearing:**

* not `SPLIT_ON_CASE_CHANGE`, so `PowerShot` stays one part — and would
  anyway, the lower-case filter having run first;
* not `SPLIT_ON_NUMERICS`, so `j2se` stays one part;
* not `CATENATE_WORDS`, `CATENATE_NUMBERS` or `CATENATE_ALL`, so no
  concatenation is emitted;
* `STEM_ENGLISH_POSSESSIVE` **is** set, so a trailing `'s` is removed from
  each part.

### 2.2 The word-break rules

The grammar implements UAX#29 word boundaries. Its macros, verbatim:

```
ALetter           = (\p{WB:ALetter}                                     | {ALetterSupp})
Format            = (\p{WB:Format}                                      | {FormatSupp})
Numeric           = ([\p{WB:Numeric}[\p{Blk:HalfAndFullForms}&&\p{Nd}]] | {NumericSupp})
Extend            = (\p{WB:Extend}                                      | {ExtendSupp})
Katakana          = (\p{WB:Katakana}                                    | {KatakanaSupp})
MidLetter         = (\p{WB:MidLetter}                                   | {MidLetterSupp})
MidNum            = (\p{WB:MidNum}                                      | {MidNumSupp})
MidNumLet         = (\p{WB:MidNumLet}                                   | {MidNumLetSupp})
ExtendNumLet      = (\p{WB:ExtendNumLet}                                | {ExtendNumLetSupp})
ComplexContext    = (\p{LB:Complex_Context}                             | {ComplexContextSupp})
Han               = (\p{Script:Han}                                     | {HanSupp})
Hiragana          = (\p{Script:Hiragana}                                | {HiraganaSupp})
SingleQuote       = (\p{WB:Single_Quote}                                | {SingleQuoteSupp})
DoubleQuote       = (\p{WB:Double_Quote}                                | {DoubleQuoteSupp})
HebrewLetter      = (\p{WB:Hebrew_Letter}                               | {HebrewLetterSupp})
RegionalIndicator = (\p{WB:Regional_Indicator}                          | {RegionalIndicatorSupp})
HebrewOrALetter   = ({HebrewLetter} | {ALetter})

// UAX#29 WB4. X (Extend | Format)* --> X
HangulEx            = [\p{Script:Hangul}&&[\p{WB:ALetter}\p{WB:Hebrew_Letter}]] ({Format} | {Extend})*
HebrewOrALetterEx   = {HebrewOrALetter}                                         ({Format} | {Extend})*
NumericEx           = {Numeric}                                                 ({Format} | {Extend})*
KatakanaEx          = {Katakana}                                                ({Format} | {Extend})*
MidLetterEx         = ({MidLetter} | {MidNumLet} | {SingleQuote})               ({Format} | {Extend})*
MidNumericEx        = ({MidNum} | {MidNumLet} | {SingleQuote})                  ({Format} | {Extend})*
ExtendNumLetEx      = {ExtendNumLet}                                            ({Format} | {Extend})*
HanEx               = {Han}                                                     ({Format} | {Extend})*
HiraganaEx          = {Hiragana}                                                ({Format} | {Extend})*
```

`{…Supp}` are the supplementary-plane companions from
`SUPPLEMENTARY.jflex-macro`, included by the grammar; `\p{Blk:…}` is the
`Blocks.txt` property and `\p{LB:…}` the `LineBreak.txt` one, which is why
both files are pinned.

### 2.3 The token types

Rules, in the grammar's own order — JFlex takes the longest match and, on a
tie, the earliest rule:

| Rule | Type | Meaning |
| --- | --- | --- |
| `{ExtendNumLetEx}* {NumericEx} ( ( {ExtendNumLetEx}* \| {MidNumericEx} ) {NumericEx} )* {ExtendNumLetEx}*` | `<NUM>` | a run of numerics, WB8/WB11/WB12/WB13a/WB13b |
| `{HangulEx}+` | `<HANGUL>` | |
| `{KatakanaEx}+` | `<KATAKANA>` | |
| the word rule (WB5–WB7c, WB9, WB10, WB13, WB13a, WB13b) | `<ALPHANUM>` | letters, numbers and the mid-characters that join them |
| `{ComplexContext}+` | `<SOUTHEAST_ASIAN>` | `\p{LB:Complex_Context}` kept together, as ICU does |
| `{HanEx}` | `<IDEOGRAPHIC>` | **one** character per token |
| `{HiraganaEx}` | `<HIRAGANA>` | one character per token |
| `{RegionalIndicatorEx} {RegionalIndicatorEx}+ \| [^]` | — | consumed and **not** emitted |

The last rule is what discards everything else: punctuation, whitespace and
a lone regional indicator produce no token at all.

The word rule, verbatim, because its shape is what §2.4 turns on:

```
{ExtendNumLetEx}*  ( {KatakanaEx}          ( {ExtendNumLetEx}*   {KatakanaEx}                           )*
                   | ( {HebrewLetterEx}    ( {SingleQuoteEx}     | {DoubleQuoteEx}  {HebrewLetterEx}    )
                     | {NumericEx}         ( ( {ExtendNumLetEx}* | {MidNumericEx} ) {NumericEx}         )*
                     | {HebrewOrALetterEx} ( ( {ExtendNumLetEx}* | {MidLetterEx}  ) {HebrewOrALetterEx} )*
                     )+
                   )
({ExtendNumLetEx}+ ( … the same group … )
)*
{ExtendNumLetEx}*
```

### 2.4 Longest match is not greedy match

JFlex matches the **longest** string the rule accepts, and for this rule
that is not what taking each alternative as far as it goes produces. The
`( … )+` has three alternatives, two of which begin on a Hebrew letter,
and a *shorter* first alternative can let a later one reach further.

`אב'` is the case, and it is in the corpus:

* the letter-run alternative, taken greedily, consumes both Hebrew letters
  and stops at 2 — the apostrophe is no letter, and no alternative
  starts on one;
* the accepting split is the letter run over `א` alone, then WB7a's
  `{HebrewLetterEx} {SingleQuoteEx}` over `ב'`, which reaches 3.

Oak's own analyzers produce the three-character token, and froe's tokenizer
therefore simulates every alternative at once — one left-to-right pass
over the atoms, keeping the last position at which an accepting state was
live — rather than committing to an alternative and running it out. The
`<NUM>` rule is simulated the same way for the same reason.

An "atom" there is one `X (Format | Extend)*` of the grammar, and consuming
that tail greedily is safe: the `Word_Break` classes are disjoint, so no
element of any rule begins with a `Format` or an `Extend` and a shorter
tail can never let a longer match through.

### 2.5 Length, offsets and skipped positions

```java
private int maxTokenLength = StandardAnalyzer.DEFAULT_MAX_TOKEN_LENGTH;   // 255
…
if (scanner.yylength() <= maxTokenLength) {
  posIncrAtt.setPositionIncrement(skippedPositions+1);
  scanner.getText(termAtt);
  final int start = scanner.yychar();
  offsetAtt.setOffset(correctOffset(start), correctOffset(start+termAtt.length()));
  …
} else
  skippedPositions++;
```

* **255 UTF-16 code units**, and a token above it is **dropped**, not
  truncated — and its position is not merely skipped: the *next* token's
  increment carries it, so the dropped token still occupies a position.
* Offsets are the scanner's character offsets into the value.
* `correctOffset` is the identity here: Oak inserts no character filter.

The end state:

```java
public final void end() throws IOException {
  super.end();
  int finalOffset = correctOffset(scanner.yychar() + scanner.yylength());
  offsetAtt.setOffset(finalOffset, finalOffset);
  posIncrAtt.setPositionIncrement(posIncrAtt.getPositionIncrement()+skippedPositions);
}
```

`super.end()` clears the attributes, which sets the position increment to
0, and then the skipped count is added. **So the final increment is the
number of tokens dropped since the last emitted one, and the final offset
is how far the scanner read** — which is the whole value, the last rule
consuming everything it does not emit. Both matter: §7 shows them
composing across several values of one field.

## 3. The lower-case filter

`analysis/core/LowerCaseFilter.java` over
`analysis/util/CharacterUtils.java`:

```java
charUtils = CharacterUtils.getInstance(matchVersion);   // JAVA_5 at 4.7
…
public final void toLowerCase(final char[] buffer, final int offset, final int limit) {
  for (int i = offset; i < limit;) {
    i += Character.toChars(Character.toLowerCase(codePointAt(buffer, i, limit)), buffer, i);
  }
}
```

**Per code point, through `Character.toLowerCase(int)` — the running JVM's
own table, not Lucene's and not Unicode 6.3's.** A consumer on Temurin 21
lower-cases by Temurin 21's Unicode; the tokenizer beside it still breaks
words by Unicode 6.3. The two versions are genuinely different in one
chain, and a port that unifies them is wrong twice over.

froe therefore does not read a case table out of a Unicode file. The
consumer's own table is the truth, and task 1003 enumerates it from the
pinned image's JVM through the judge — every code point whose lower case
differs from itself, dumped and committed as a fixture.

The filter changes no offset and no position: it rewrites the term in
place.

**Single-code-point mapping only.** `Character.toLowerCase(int)` returns
one code point; the lower case of `İ` (U+0130) is `i` under it, where
full case folding would give `i` plus a combining dot. Lucene's filter is
the one Oak uses, so froe reproduces its one-to-one mapping and not the
Unicode full mapping.

## 4. The word delimiter filter

`analysis/miscellaneous/WordDelimiterFilter.java` and its
`WordDelimiterIterator`.

### 4.1 The character-type table

The constructor Oak calls takes no table, so the iterator's default is
used:

```java
static {
  byte[] tab = new byte[256];
  for (int i = 0; i < 256; i++) {
    byte code = 0;
    if (Character.isLowerCase(i))      code |= LOWER;
    else if (Character.isUpperCase(i)) code |= UPPER;
    else if (Character.isDigit(i))     code |= DIGIT;
    if (code == 0) code = SUBWORD_DELIM;
    tab[i] = code;
  }
  DEFAULT_WORD_DELIM_TABLE = tab;
}
```

with `LOWER = 0x01`, `UPPER = 0x02`, `DIGIT = 0x04`, `SUBWORD_DELIM = 0x08`,
`ALPHA = 0x03` and `ALPHANUM = 0x07`.

**Below 256 the table decides; at 256 and above `Character.getType` does**:

```java
case Character.UPPERCASE_LETTER: return UPPER;
case Character.LOWERCASE_LETTER: return LOWER;
case Character.TITLECASE_LETTER:
case Character.MODIFIER_LETTER:
case Character.OTHER_LETTER:
case Character.NON_SPACING_MARK:
case Character.ENCLOSING_MARK:
case Character.COMBINING_SPACING_MARK:  return ALPHA;
case Character.DECIMAL_DIGIT_NUMBER:
case Character.LETTER_NUMBER:
case Character.OTHER_NUMBER:            return DIGIT;
case Character.SURROGATE:               return ALPHA|DIGIT;   // prevent splitting
default:                                return SUBWORD_DELIM;
```

Both halves are the **running JVM's** tables again, like §3's case mapping
and unlike §2's word breaks. The same fixture answers both.

### 4.2 What Oak's flags make it do

With `GENERATE_WORD_PARTS | GENERATE_NUMBER_PARTS | STEM_ENGLISH_POSSESSIVE`
and no split-on-case-change and no split-on-numerics:

* the token is split at runs of `SUBWORD_DELIM` characters — anything that
  is not a letter or a digit;
* **no split at a case change** and **no split between letters and
  digits**, so `PowerShot` and `j2se` each stay one part;
* a trailing `'s` (an apostrophe of any of the forms the iterator accepts
  followed by `s` or `S`, at the end of a part) is removed;
* under `PRESERVE_ORIGINAL` the undelimited original term is emitted
  beside the generated parts.

Each generated part carries the offsets of its own span within the original
token. The position rule is `position(boolean inject)`:

```java
private int position(boolean inject) {
  int posInc = accumPosInc;
  if (hasOutputToken) {
    accumPosInc = 0;
    return inject ? 0 : Math.max(1, posInc);
  }
  hasOutputToken = true;
  if (!hasOutputFollowingOriginal) {
    // the first token following the original is 0 regardless
    hasOutputFollowingOriginal = true;
    return 0;
  }
  accumPosInc = 0;
  return Math.max(1, posInc);
}
```

so: the first part of a token carries the increment accumulated from the
input, every later part carries **at least 1**, and — under
`PRESERVE_ORIGINAL` — the first generated part *after* the original carries
**0**, sharing the original's position. A token the filter does not split
at all passes its increment through unchanged.

## 5. The analyzer the definition builds

`plugins/index/lucene/LuceneIndexDefinition.java`:

```java
private Analyzer createAnalyzer() {
  Analyzer result;
  Analyzer defaultAnalyzer = LuceneIndexConstants.ANALYZER;
  if (analyzers.containsKey(ANL_DEFAULT)) {
    defaultAnalyzer = analyzers.get(ANL_DEFAULT);
  }
  if (!evaluatePathRestrictions()) {
    result = defaultAnalyzer;
  } else {
    Map<String, Analyzer> analyzerMap = Map.of(
        FieldNames.ANCESTORS, new TokenizerChain(new PathHierarchyTokenizerFactory(Collections.emptyMap())));
    result = new PerFieldAnalyzerWrapper(defaultAnalyzer, analyzerMap);
  }
  //In case of negative value no limits would be applied
  if (maxFieldLength < 0) {
    return result;
  }
  return new LimitTokenCountAnalyzer(result, maxFieldLength);
}
```

Three facts:

1. **`:ancestors` gets a path-hierarchy chain**, and only when
   `evaluatePathRestrictions` is on. Otherwise every field goes through the
   default analyzer.
2. **The whole thing is wrapped in the token-count cap** at
   `maxFieldLength`, whose default is `DEFAULT_MAX_FIELD_LENGTH` = 10,000.
3. **A negative `maxFieldLength` means no cap at all**, not a cap of zero.

### 5.1 What a `maxFieldLength` of zero actually does

The plan's task text says the limiting filter refuses a limit below one and
that Oak's editor catches the refusal per document. **That is a later
Lucene's behaviour, not 4.7.2's.** In the pinned
`analysis/miscellaneous/LimitTokenCountFilter.java` there is no such check:

```java
public LimitTokenCountFilter(TokenStream in, int maxTokenCount, boolean consumeAllTokens) {
  super(in);
  this.maxTokenCount = maxTokenCount;
  this.consumeAllTokens = consumeAllTokens;
}

public boolean incrementToken() throws IOException {
  if (exhausted) return false;
  else if (tokenCount < maxTokenCount) { … }
  else { while (consumeAllTokens && input.incrementToken()) {} return false; }
}
```

and `LimitTokenCountAnalyzer`'s constructor passes the count through
untouched. With `maxTokenCount = 0` the first `incrementToken` finds
`0 < 0` false and returns `false` immediately: **every analyzed field is
silently empty**, and no exception is thrown, no document is dropped, and
the index is written.

So a definition with `maxFieldLength = 0` is not an error Oak reports; it
is an index whose analyzed fields hold nothing. froe still refuses it by
name — an index that cannot answer a fulltext query is not one a reindex
should produce silently — but the refusal is froe's own choice and not a
reproduction of an Oak refusal, and task 1005 records it that way.

### 5.2 The second wrapper, and the two fields the cap never reaches

`plugins/index/lucene/writer/IndexWriterUtils.getIndexWriterConfig`:

```java
Analyzer definitionAnalyzer = definition.getAnalyzer();
Map<String, Analyzer> analyzers = new HashMap<String, Analyzer>();
analyzers.put(FieldNames.SPELLCHECK, new ShingleAnalyzerWrapper(LuceneIndexConstants.ANALYZER, 3));
…
if (!definition.isSuggestAnalyzed()) {
  analyzers.put(FieldNames.SUGGEST, SuggestHelper.getAnalyzer());
}
Analyzer analyzer = new PerFieldAnalyzerWrapper(definitionAnalyzer, analyzers);
IndexWriterConfig config = new IndexWriterConfig(VERSION, analyzer);
```

The definition's analyzer — cap and all — becomes the **default** of a
second per-field wrapper. A per-field entry replaces it whole, so:

* **`:spellcheck`** is analyzed by `ShingleAnalyzerWrapper(ANALYZER, 3)`:
  Oak's *shared* analyzer instance under a shingle filter, **not** the
  definition's, and **not** capped.
* **`:suggest`** is analyzed by `SuggestHelper.getAnalyzer()` unless the
  definition sets `suggestAnalyzed`, and is likewise **not** capped.
* Every other field, `:ancestors` included, keeps the definition's
  analyzer and its cap.

The similarity entries — `LSHAnalyzer` for a `useInSimilarity` property —
are out of scope for this plan and froe refuses a definition that declares
one.

## 6. The other chains

### 6.1 The path-hierarchy chain, for `:ancestors`

`analysis/path/PathHierarchyTokenizer.java`, built by
`PathHierarchyTokenizerFactory` with an empty parameter map, so both
defaults hold:

```java
public static final char DEFAULT_DELIMITER = '/';
public static final int DEFAULT_SKIP = 0;
```

One token per ancestor prefix, each starting at offset 0 and ending at the
prefix's end; the first token carries a position increment of 1 and every
later one **0**, so they all occupy position 0. The end state sets both
offsets to the length of the input.

**`:ancestors` holds the node's *parent* path, not its own** —
`LuceneDocumentMaker.indexAncestors` is
`doc.add(newAncestorsField(PathUtils.getParentPath(path)))`, with
`newDepthField(path)` over the node's own path beside it. For
`/content/interop/page` the field's value is `/content/interop`, and the
chain's terms are therefore

```
/content            offsets 0..8   position 0
/content/interop    offsets 0..16  position 0
```

— not `content`, `interop`, which is what the default analyzer would have
produced.

### 6.2 The suggest tokenizer

`plugins/index/lucene/util/CRTokenizer.java`:

```java
public class CRTokenizer extends CharTokenizer {
  public CRTokenizer(Version matchVersion, Reader input) { super(matchVersion, input); }
  @Override protected boolean isTokenChar(int c) { return c != '\n'; }
}
```

A character tokenizer that splits on newlines only — and, like every
character tokenizer, at a maximum word length:

```java
private static final int MAX_WORD_LEN = 255;
…
length += Character.toChars(normalize(c), buffer, length);
if (length >= MAX_WORD_LEN) // buffer overflow! make sure to check for >= surrogate pair could break == test
  break;
```

The check is **after** the code point is appended, so a token whose 255th
and 256th units are a surrogate pair is cut at **256** units. A suggest
value longer than that yields several terms rather than one.

### 6.3 The shingle chain, for `:spellcheck`

`analysis/shingle/ShingleFilter.java` under
`ShingleAnalyzerWrapper(ANALYZER, 3)`, so Oak's own three-stage analyzer
feeds it and the shingle sizes are the wrapper's defaults with the maximum
raised to 3:

```java
public static final String DEFAULT_FILLER_TOKEN = "_";
public static final int DEFAULT_MIN_SHINGLE_SIZE = 2;
public static final String DEFAULT_TOKEN_TYPE = "shingle";
public static final String DEFAULT_TOKEN_SEPARATOR = " ";
private boolean outputUnigrams = true;
```

So: unigrams **are** emitted beside the shingles, a shingle joins its
tokens with a single space, a gap in the input contributes the filler `_`,
and a shingle's token type is `shingle`. A shingle carries the offsets
spanning its first and last token and a position increment of 0 — it shares
the position of the unigram it starts at — while each unigram advances the
position by one.

## 7. How several values of one field compose

Lucene's own inverter opens **one token stream per field instance**, and
Oak adds one field per property value, so a multi-valued property is
several streams and not one. `index/DocInverterPerField.processFields`
composes them:

```java
if (i > 0) {
  fieldState.position += docState.analyzer == null ? 0 : docState.analyzer.getPositionIncrementGap(fieldInfo.name);
}
… tokens …
stream.end();
fieldState.position += posIncrAttribute.getPositionIncrement();
fieldState.offset += offsetAttribute.endOffset();
…
fieldState.offset += docState.analyzer == null ? 0 : docState.analyzer.getOffsetGap(fieldInfo.name);
```

`Analyzer`'s defaults are a **position-increment gap of 0** and an
**offset gap of 1**, and neither Oak's analyzer nor any wrapper in the
chain overrides them.

So, after each value: the chain's **end state** contributes its position
increment and its end offset, and then the gaps. That makes each chain's
end state part of this specification, and it differs by chain:

| Chain | Final position increment | Final offset |
| --- | --- | --- |
| Oak's analyzer (standard tokenizer at the source) | the number of over-long tokens dropped since the last emitted one | how far the scanner read — the whole value |
| the same under the token-count cap, **when the cap bites** | what was dropped immediately *before* the last token the cap kept | the end of that token |
| path hierarchy (`:ancestors`) | 0 | the length of the input |
| the suggest tokenizer (`:suggest`) | 0 | the length of the input |
| the shingle chain (`:spellcheck`) | the wrapped chain's, which is Oak's analyzer's | the wrapped chain's |

**The cap changes the end state**, and that is worth stating plainly
because it is the opposite of what a filter usually does.
`LimitTokenCountAnalyzer`'s two-argument constructor passes
`consumeAllTokens = false`, so on reaching its limit the filter returns
`false` **without pulling the stream below it**. Nothing has drained the
tokenizer, and `end()` therefore reports where the scanner happens to
stand: `scanner.yychar() + scanner.yylength()` is the end of the last
token it matched, not the end of the value, and `skippedPositions` still
holds what `incrementToken` zeroed on entry and counted before that
token. A stream the cap does *not* bite is unaffected, since the filter
then drains its input as usual.

Corpus line 28 of task 1003's fixture is the case: 10,050 values of `f`
separated by spaces, capped at 10,000, and Oak's own judge records the end
state as increment 0, offset 19,999 — the end of the ten-thousandth
token — against an input 20,100 characters long.

The `:suggest` row is the second place where reading the code beats
reading the shape. `CharTokenizer.incrementToken` sets `finalOffset`
twice: to each token's end as it is emitted, and to everything the reader
consumed on the call that returns `false`. Lucene always calls
`incrementToken` until it is false before `end()`, so the second
assignment is the one that survives, and a value ending in a newline
reports past its last token.

## 8. Numerics

`lucene-core`'s trie encoding, from
`oak-lucene/src/main/java/org/apache/lucene/util/NumericUtils.java` and
`analysis/NumericTokenStream.java`.

### 8.1 The precision step

```java
public static final int PRECISION_STEP_DEFAULT = 4;
```

and `LongField`, `IntField` and `DoubleField` all document their default as
`NumericUtils#PRECISION_STEP_DEFAULT` (4). Oak builds its numeric fields
through `plugins/index/lucene/FieldFactory.java`, which constructs them
with the value alone and therefore takes that default. A double is indexed
as a long — §8.3 — so all three use the same step.

At a step of 4 a 64-bit value yields **16** terms (shifts 0, 4, 8, … 60)
and a 32-bit value **8** (shifts 0, 4, … 28).

### 8.2 The prefix coding

```java
public static final byte SHIFT_START_LONG = 0x20;
public static final int BUF_SIZE_LONG = 63/7 + 2;   // 11
public static final byte SHIFT_START_INT  = 0x60;
public static final int BUF_SIZE_INT = 31/7 + 2;    // 6
```

A term is the shift byte — `SHIFT_START_LONG + shift` for a long,
`SHIFT_START_INT + shift` for an int — followed by the value's bits above
the shift, seven to a byte, most significant group first, with the sign bit
flipped so the byte order is the numeric order.

**Every shift level is a term at the same position**, with a position
increment of 1 on the first and 0 on the rest, and the field's index
options are `DOCS_ONLY` — `NumericTokenStream` sets no frequency and no
offset, and the field types omit them.

### 8.3 The three types Oak writes

| Oak's type | Lucene field | Encoding |
| --- | --- | --- |
| `LONG` | `LongField` | the value, prefix-coded as a long |
| `DATE` | `LongField` | **the epoch millisecond** of the date, prefix-coded as a long |
| `DOUBLE` | `DoubleField` | `NumericUtils.doubleToSortableLong`, then prefix-coded as a long |
| the synthetic `:depth` | `IntField` | the path's depth, prefix-coded as an int |

```java
public static long doubleToSortableLong(double val) {
  long f = Double.doubleToLongBits(val);
  if (f<0) f ^= 0x7fffffffffffffffL;
  return f;
}
```

**The sortable long is the *indexed term*'s encoding and not the doc
value's.** A `DOUBLE` doc value is the raw bits of the double
(`Double.doubleToLongBits`), which differ from the sortable long for every
negative double, for `-0.0` and for `NaN`. The two live in one field name
and mean different things; §8.1 of `lucene-oak-documents.md` states it from
the document maker's side.

## 9. Worked examples

Expected token tuples as `(term, position increment, start offset, end
offset)`. Task 1003's vectors confirm each against the judge's `analyze`
output inside the pinned image; where a table below and the judge disagree,
**the judge is right and this document is wrong**.

### 9.1 `Foo-Bar's 3rd j2se PowerShot` under Oak's analyzer

The standard tokenizer breaks at the hyphen (WB14: a hyphen is none of the
mid-classes), keeps `Bar's` together (WB7a/WB6: a single quote between
letters), keeps `3rd` together (WB9/WB10) and keeps `j2se` together for the
same reason:

```
Foo     1  0   3
Bar's   1  4   9
3rd     1  10  13
j2se    1  14  18
PowerShot 1 19 28
```

The lower-case filter rewrites each in place. The word delimiter filter
then splits at delimiters and strips the possessive:

```
foo        1  0   3
bar        1  4   7
3rd        1  10  13
j2se       1  14  18
powershot  1  19  28
```

`bar's` loses its `'s` under `STEM_ENGLISH_POSSESSIVE`, and the apostrophe
is a delimiter besides; `3rd`, `j2se` and `powershot` survive whole for
want of `SPLIT_ON_NUMERICS` and `SPLIT_ON_CASE_CHANGE`. The end state is
increment 0, offset 28.

Under `analyzers/@indexOriginalTerm` the undelimited original joins each
split token at its own position: `bar's` beside `bar`.

### 9.2 `/content/interop` under the path-hierarchy chain

The value is the *parent* path of `/content/interop/page`:

```
/content          1  0  8
/content/interop  0  0  16
```

End state: increment 0, offset 16.

### 9.3 `Foo Bar` under the `:spellcheck` chain

Oak's analyzer gives `foo`, `bar`; the shingle filter at a maximum size of
3 emits the unigrams and the shingles that fit:

```
foo      1  0  3
foo bar  0  0  7
bar      1  4  7
```

With a third token the size-3 shingle appears too, spanning the first and
third tokens' offsets at the first's position.

### 9.4 `one\ntwo` under the `:suggest` chain

The suggest tokenizer splits on the newline alone:

```
one  1  0  3
two  1  4  7
```

### 9.5 `1` as a `LONG`

Sixteen terms at one position, shifts 0 through 60, the first carrying a
position increment of 1 and the rest 0, in `DOCS_ONLY` with no offsets.
The shift-0 term is `0x20` followed by the seven-bit groups of
`0x8000000000000001` — the sign-flipped value — and each later term drops
the low four bits before coding.

## 10. AEM safety invariants

* **The word-break tables are Unicode 6.3.0 and the case tables are the
  consumer's JVM.** Reproducing either with the other's version changes
  terms, and a changed term is a query that stops matching.
* **froe reproduces no consumer-registered analyzer.** A definition whose
  `analyzers` node names a class froe does not implement is refused by
  name rather than approximated.
* **The cap is per field value, not per field.** A multi-valued property of
  three values under a cap of 10,000 may hold 30,000 tokens.
* **`:spellcheck` and `:suggest` are never capped**, because the writer's
  own per-field wrapper replaces the definition's analyzer for them whole.
* **A `maxFieldLength` of zero is silent in 4.7.2**, not an error: §5.1.
